2026-09-22 实机（经 8088，`qa/fixtures/rag/公司年报.pdf` 1,682,689 B → 263,910 字 → 587 块，bge-m3 / 1024 维）：

- **本次复验实测：`total_time=131.898s`**；后端日志 `[kb] 向量化完成 chunks=587 batches=37 durationMs=134663`
  ⇒ **≈3.6 s/批**（解析 0.96s、分块瞬时；总耗时略小于向量化耗时是日志取值口径差异，非矛盾）。
- 同日更早一次：**129.75s** ⇒ 两次一致，**3.6 s/批 是可复现的口径，不是单次抖动**。
- **设计稿 §7.2 写的 2.1 s/批 ⇒ 80~90s 是早期估算，偏低约 1.5~2 倍**：
  TC-03 若照"80~90s"断言会**假失败**。**已定案（主会话裁决 + 设计 §7.2）**：耗时**不当硬判据** ——
  只记录实测值，上界用"必须 < 300 s"（**与前端超时同源**，这才是这个数字有意义的地方）；
  **不要再引入"90~180s"这类新窗口**，它同样会随负载漂移而假失败。

**Why:** 这个数决定三件事的取值 —— ① 前端上传超时（现 300s ⇒ 余量仅约 2.3×，不是"随便设大"）；
② qa 用例的断言区间；③ "上传是不是太慢"的定性（按实测**不算**缺陷，属 embedding 批量调用的真实成本）。

**How to apply:** 再遇到"上传比设计慢一倍"，**先对这条**（预期就是 ~130s），别去查代码。
⚠️ 以下任一变化都会让这个数失效、必须重测：改分块参数、换 embedding 模型、机器负载/并发变化。
