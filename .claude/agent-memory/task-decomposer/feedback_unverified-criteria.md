起草 / 拆解任务文档时，**凡涉及运行时状态的判据**（容器 healthy/running、退出码、端口响应、探活结果），一律标注「需实测确认」，不得把未验证的观察写成验收标准。

**Why**：`docs/drafts/环境检查脚本.md` 是一份未复核草稿，8 处判据错误全部源于「凭印象写运行时状态」：后端写 8080（实为 8089）、前端写 80（宿主实为 8088）、写了必然 404 的反代路径 `/api/actuator/health`、要给**已有** healthcheck 的容器「补」healthcheck、把阶段1（`CREATE EXTENSION` / `tenant_id`）与阶段2（`/api/ai/ping`）才存在的东西当成现在的检查项。其中「前端容器只是 Started 不是 Healthy」这条观察**来源不明**（当时贴出的是 `docker images` 镜像列表，无健康状态列），却直接派生出「要不要补 healthcheck」这个假任务。

**How to apply**：
1. 写验收标准前先回仓库核实 —— `.env` / `docker-compose.yml` / `application.yml` / `nginx.conf` 是端口与探活判据的事实源，不引用第二手描述；
2. 无法核实的写成「需实测确认」，并说明验证方式，不写成断言；
3. 范围出现**语义冲突**时（草稿把「运行期巡检」混进「启动前置自检」，两者失败处理相反），列出**选项 + 取舍 + 推荐**，说明每个选项对交付物清单的影响面，但**不替用户拍板**；
4. 顺手产出「**明确不做**」清单，防止后续 agent 照草稿把已否决的方案重新生成。
6. **对账类任务里，别人给你的「漂移清单」本身也是二手描述**：逐条回仓库核实，不要照抄。2026-09-12 用户给的清单写「0.3.4 未开工（这个是真的没做）」，实际 `wsl.abc.md` 早已交付（2026-09-03，与 0.1 同批，见 `docs/agent-log/20260903-step10-wrapup.md`），真正缺的只有 README 一节 —— 照抄就会把一处已完成的工作记成未做。**观察到与用户陈述相反的事实时，据实写进文档并在汇报里单独说明**（既不静默改，也不照抄）。同理，清单里说「已实现」的项也要核实**是否只是落盘**（见 [[implemented-vs-accepted]]）。
7. 用户**拍板后**要全量同步引用点，别只改被点名的那一处：① 把「待确认 / 范围待确认」小节就地转成「决策记录」（保留被否决方案的**一行**理由备查）；② 逐处 grep「待确认」清掉悬空引用（`输入` / `输出` / `依赖` / `阶段交付物` / `完成状态` / `docs/核心任务.md`）；③ 若决策新增了原子任务，**必须回填被它阻塞者的依赖行**（本轮新增 `probe.sh` 后，`up.sh` 的 `输入` / `依赖` 两行都要补，否则依赖图失真）；④ `docs/核心任务.md` 的交付物描述按用户授权加项，但**只加被点名的那一项**；⑤ 进度行若还写着已被推翻的「待确认」，属事实性错误，须一并订正并在汇报中单独说明。
