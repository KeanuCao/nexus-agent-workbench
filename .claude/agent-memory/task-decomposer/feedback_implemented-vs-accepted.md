对账 / 更新任务文档时，把工作状态拆成**三态**记录，不要用「未开工 ↔ 已完成」二态：

1. **已实现**（文件落盘、`bash -n` 等静态检查通过）；
2. **已验证**（只读实跑：跑出 `PASS/WARN/FAIL` 计数、幂等复跑一致）—— 这是**证据**，不是验收；
3. **已验收**（对方点名的验收方式全部走完，如设计文档 §7 的「逐项触发 PASS/WARN/FAIL 各路径」）。

**未过实机验收的子项一律不勾 `- [ ]`**，并在勾选清单里分「已验证 / 未验证（勾选前必须补）」两段 —— 沿用本仓库 0.4 条目的既有记法。

**Why**：2026-09-12 对账 0.3 时用户明确要求「已实现 ≠ 已验收，请把状态写准确」。当时四个脚本全部落盘、其中两个已实跑出漂亮计数，但真实缺口仍在（`up.sh` 端到端从未跑过、`check-env.sh` 负路径没触发过、前端容器重建后 WARN 才归零）。二态记法会让这些被「已实现」三个字吞掉，等到验收现场才发现。

**How to apply**：
1. 状态表至少四列：`产物（行数）｜已实现｜已验证（只读实跑 / 静态复核）｜待验收（完成前不勾选）`；「待验收」列写**具体动作**（哪条命令、看哪个数字从几变到几），不写「待验证」了事；
2. **静态复核也是有效证据，但必须写清边界**：如「`up.sh` / `check-health.sh` 的**判定逻辑**未内联探针命令、未出现宿主端口与模型名字面量（仅人读提示文案里有容器内端口）」—— 说清「没查什么」比笼统的「已检查」有用；
3. **修复记录必须带生效条件**：改了 `docker-compose.yml` 但容器没重建 = **尚未生效**，如实标注「需 `docker compose up -d` 重建后才可见」，并给出验证判据（重建后复跑，`WARN 1` → `0`）。「改完 = 好了」是本项目反复踩的坑；
4. 同一事实只在一处记全，其余位置给指针（勾选清单写「逐项状态见 0.3 的现状表」），避免两处漂移。
