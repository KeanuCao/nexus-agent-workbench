拆阶段任务时，**先把"用户本人必须手工完成"的部分单独拆出来**，与 AI/Agent 可执行的任务分成两套独立勾选清单。

每项手工任务（编号 M1、M2…）写清**五件事**：
① 为什么必须手工（AI 做不了的原因：浏览器/GitHub 平台操作、凭据、资源与账号决策）；
② 前置条件；③ 逐步操作（能引用既有手册命令就直接引用，别另造一套）；④ **交接物**（完成后必须回传给 AI 的信息 —— 如发行版名、runner 标签、已配置的 secret **键名**、端口确认）；
⑤ 完成判据（用户自己能看见/验证的现象）。
文末给一张 **M 任务 ↔ AI 子任务**的阻塞关系图（Mermaid 或编号列表），并在子任务里标注"压在哪个 M 之后"。

**Why**：用户本次明确说"核心诉求是把需要用户本人手工完成的部分单独分解出来"。
动机是**一人工程的执行成本全在用户身上**（见 [[qa-cost-vs-coverage]] 同一根源）——手工项与 AI 项混在一张清单里，
就看不清"到底卡在谁身上"，AI 也容易假设前置已就绪、往下写出无法验收的代码。
凭据类（SMTP / API key / git）单列还因为它们**不能过 AI**（项目部署脚本已写死"不打印密钥"）。

**How to apply**：任何阶段只要包含"只有人能做"的动作（建环境、注册 runner、平台侧配置、密钥、资源取舍决策、
浏览器侧首次验收），就照此结构写；同时把「不被任何 M 阻塞、可以立刻开工」的子任务显式点出来（本次是前端定位属性 5.3）。
纯代码阶段（无手工项）不套这个模板。
