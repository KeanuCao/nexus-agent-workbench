**规则**：判据复核第一问 —— **「如果被测的那件事完全失效，这条用例的观察会不会变？」** 不变 = 假阴性，得重新设计或明确标注"本条不覆盖"。

**Why**：2026-09-17 复核 `TC-01-1.3-2`（两租户互不可见）时，同一轮撞到三个坑：

1. **预期的一半没有步骤**：`GET /api/auth/me` 不收任何入参、永远只回调用者自己（`AuthController.java:84-87`）
   → 预期里「admin 永远拿不到 demo 的数据」那半句**步骤一个字都没覆盖**：即便租户条件完全没注入，
   两次调用照样各回各的、一字不差。这类含糊措辞最危险 —— 它听起来像判据，其实没有对应动作。
2. **同一个码既是 PASS 又是"夹具坏了"**：签名错与"隔离生效"都回 `code=40101` → 密钥配错的夹具会**伪装成 PASS**。
3. **同一个码还兼着第三种含义**：登出后调 `/me` 的 `40101` 与「Redis 白名单里没这个 jti」也是同一个码（`TC-01-1.2-5`）。

**`40101` 那个坑后来是怎么拆开的（2026-09-17，可复用）**：判据不是"拿到 40101"，而是"**落在过滤器的第 ③ 步**"。
拆法有两层，都是**只读**观察：
- **日志按 jti 精确分流**：第 ③ 步的 warn **带 jti**（`Redis 白名单无此登录态…jti=…`），第 ② 步的两条 warn
  **不带** jti（`token 非法（type=…）` / `token 已过期`）⇒ 能与**本次** jti 对上的那一行只可能来自 ③。
  这比"看文案"强：jti 是本次运行独有的，窗口里混着别的用例的行也不会误判。
- **同一 token 的前后基线**：登出前先调一次 `/me`（200），登出后再调（401）—— 两次之间唯一的变量就是"键在不在了"；
  顺带堵住"logout 根本没要求鉴权、回 200 却什么也没做"这种假通过。
- 兜底推理链（日志取不到也能读）：② 只看 token 字节与当前时刻，而登出回了 200 ⇒ 那一刻 ②③ 都过了 ⇒ 之后的 40101 只能来自 ③。

**How to apply**：
- 设计判据时逐条问"失效时这条会不会照样通过"；假阴性的部分**明确标注覆盖不到**，并另找判据补上（例：`TC-01-1.3-5`）。
- 凡"坏掉时也回同一个码"的路径，**夹具自带一个能当场证伪的前提检查**，且不通过时**显式退出码 + 明确不给结论**
  （例：重签 token 前先用本地密钥验签一份真 token；验过才说明 40101 是隔离拒的，不是签名错）。
- 找"等价观察"的顺序仍按 charter §1：**先读被测组件的判定顺序** —— 本轮的答案就是把"够不到"退化成一份纯本地重签的
  token（零写库、零改配置、零重建），而不是去改配置或加接口。
- 复核结论若与 TC 里原有措辞冲突，**改措辞前先把"能证明什么 / 不能证明什么"写成两句话**，别把含糊留着。
