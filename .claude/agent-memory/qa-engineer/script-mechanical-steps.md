**规则**：TC「步骤」栏里凡是**需要执行者手工拼装多步命令**才能拿到判据的（典型：登录 → 从 JSON 里抠 token → 带 token 调接口），
应落到 `qa/scripts/` 的一个脚本里；步骤栏只留**一行可复制粘贴的命令 + 一句「这一步在干什么」**。

**Why**：用户 2026-09-17 手工走 TC-01-1.3-2 时原话 —— 「这个 case 逻辑上没毛病，但**我得自己拼命令，这不是人擅长的事**」。
两个具体痛点：① WSL 内**没有 jq**（也没有 node），抠 token 只能手写 `grep -o '"token":"[^"]*"' | cut -d'"' -f4`；
② 手工拼的引号/管道容易抄错，而**一旦抄错，用例失败就无法归因**（分不清产品缺陷 / 文档缺陷 / 执行偏差）——
与 TC-00-0.1-7 的速记事故是同一类失效。
分界仍然要守死：**机械动作归脚本、判断留给人**（`qa/README.md` 铁律 #2：脚本**不打 PASS/FAIL**，判据永远在 TC 的「预期」栏）。

**抽公共库的判据（2026-09-17 增）**：脚本从 2 个涨到 4 个时，用户让我评估要不要抽库，判据是
**「重复的是机械动作就抽；抽出来的库一旦开始包含判据或业务语义，就别抽」**。
结论是**抽**：四个脚本里常量与端口解析、JSON 取值、HTTP 动作、Redis 指纹、**退出路径的清理脚手架**逐字重复
（最不能各写一份的正是最后一项 —— trap 的坑若只在某一处修好，其余脚本会静默带着缺口）；
库 = `qa/scripts/lib/tc-common.sh`，用例独有的东西（如重签 token 的夹具逻辑、账号口令、节标题编号）留在各自脚本里。
**时机论证**：换库时两个既有脚本**用户还没跑过**（TC 的「实测」栏为空）⇒ 没有已记录的结论会被重构作废，此刻零成本。

**How to apply**：
- 复核/设计 TC 时，看到步骤里有连续 ≥2 条命令、或需要"把上一条的输出喂给下一条"，先问「这段能不能收进 `qa/scripts/` 的一个脚本」。
- 脚本必须同时给出**作用域声明 / 幂等清理 / 无害性自证**三样，且**先取指纹再动手**（见 [[fixture-cleanup-claims]]）。
- 脚本的退出码只表示「动作做没做成」，**不是判据**；这一点要写进脚本头与 TC 步骤栏，避免执行者拿退出码当结论。
- **重构既有脚本时，用「干跑输出归一化后逐字节 diff」证明行为没变**（归一化只去随机项：jti / token 串）：
  本轮 4 个用例 diff 全空、只有 1 处**有意**新增的说明行有差异 —— 比"我看着没改到"强得多，且成本很低。
  （做法：重构前先把干跑输出存成 baseline，再跑同一套干跑驱动，`diff -u` 两版归一化结果。）
- 进度：2026-09-17 已脚本化 `1.2-4` / `1.2-5` / `1.3-2` / `1.3-5` 四条（`qa/scripts/tc01-*.sh`）；
  新脚本的**真后端路径仍未实测**，由用户手工验收。
