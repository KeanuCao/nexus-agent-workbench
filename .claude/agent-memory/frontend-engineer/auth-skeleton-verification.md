实现 1.5 时从契约（`docs/api/README.md` §1.4 / §5）+ 守卫规则推导出的三条要点，**不在任何设计文档里**，但实机验收/排查必然撞上：

1. **`/api/health` 是白名单接口，永不因 token 失效返回 401。** 目前能触发 401 的受保护接口只有 `/api/auth/me`（由路由守卫在"刷新后首次进入受保护页"时调用）与 `/api/auth/logout`。所以验收 1.5-3（401 自动登出）时点控制台上的"刷新"健康面板**不会有任何反应**，必须刷新页面、或在别处登出后用同一页面继续操作。
2. **改坏 localStorage 里的 token，刷新后才生效。** store 的 token 在内存里是权威值，运行期不重读 localStorage —— 这是 SPA 的固有语义，不是缺陷。
3. **`restore()` 失败时无论什么原因（401、超时、连不上）都必须清空本地登录态。** 若失败后仍留着 token，守卫规则③（有 token 未核实 → 去核实）与规则①（已登录访问 /login → 回控制台）会互相把用户弹来弹去 → 无限重定向。fail-closed 的代价是"后端全挂时用户会被请回登录页"，这是有意的。

**Why:** 这三条是跨文件推理的产物（守卫三条规则 × 白名单 × Redis 白名单登录态），单看任一文件都看不出来；当时无人可问，靠逐条推演得出。

**How to apply:** 用户或后续 agent 报「401 没自动登出」「改了 token 没反应」时，先按第 1、2 条排查再怀疑代码；任何人改动守卫规则或 `restore()` 时，必须保住第 3 条的防环设计。相关：[[api-contract-source]]
