**规则**：前端注释、UI 文案、README 里凡出现"实测可推翻"的数字（耗时、批数、秒/批、体积…），
一旦有实测值，就**当场订正到实测口径**，并且**保留痕迹**：写明旧估算是什么、为什么偏低（错在哪）、
偏差倍数、以及这个数字**在判据体系里的地位**。耗时类数字一律标注"**只当参考记录值、不当硬判据**"。

**Why:** 2026-09-22 端到端实测（经 8088，两次一致：131.9 s / 129.75 s）推翻了 `kb.ts`
`UPLOAD_TIMEOUT_MS` 注释里沿用的设计初版估算"37 批 × 约 2.1 s/批 ⇒ 80~90 秒"——那是**宿主直连
Ollama** 的估算，偏低 1.5~2 倍。数字型断言最危险的下场是**变成 flaky 判据**：TC-03 里"120~140 秒"
与"80~90 秒"两套窗口**都已被删**，只留"< 300 s"一条上界（与前端逐请求超时同源）。前端注释里若留着
旧数字，后来者会照着写断言/写判据，把假失败请回测试里。

**How to apply:**
- 订正落笔的三件套：① 实测值（含"经哪个端口/什么硬件/几次一致"）② 旧估算**已作废**+ 偏差倍数
  ③ 这个数字的用途（如 `300_000` 的价值在于对 131.9 s 有 ≈2.3× 余量，不是"卡着估算值放"）。
- **UI 文案也算订正对象**（用户明确把"文案"列进 grep 范围）：本次把知识库页
  "大文件可能要 1~2 分钟"改成"实测约 2 分钟出头、随机器负载浮动"。
- 边界：这类任务**只改解释性文字**——超时值、请求逻辑、`Content-Type` 那两处 415 修复
  一个字都不动；改完跑 `npm --prefix frontend run type-check`（vue-tsc）并**报退出码**；
  **不提交**（commit 归主会话，见 [[manual-push-and-merge]] 的同类分工）。
- 顺带 grep 时**分清"活断言"与"历史记录"**：`docs/agent-log/*` 里同款旧数字是当时快照，
  不要改写历史；`docs/api/README.md` 与 `openapi.yaml` 属**后端契约**（我的红线：不改 API 文档）
  —— 发现残留只**上报**，不动手。
