# Maven 构建失败诊断（junit-jupiter-params 传输截断）

- **Agent**：backend-engineer ｜ **耗时**：约 3 分钟 ｜ **task-id**：a25ba1709e8c30834

## 做了什么

事件：`nexus-backend` 首次构建，6 模块中 5 个 SUCCESS，`nexus-start` 失败于
`Could not transfer artifact org.junit.jupiter:junit-jupiter-params:jar:5.10.5 from/to aliyun-central: Premature end of Content-Length delimited message body (expected: 586,031; received: 524,288)`。

- **推翻了"512KB 边界 = 确定性故障"的假设**（该假设由主会话提出）：`received` 是**客户端消费侧计数器**，Maven 定长缓冲循环读，任何记录**必然是缓冲大小的整数倍**；524288 = 64×8192 = 8×65536，只是约 70 个可能落点之一，"恰好 512KB"的概率是 **1/70 量级而非 1/586031**。
- **给出更强的反证**：同一构建此前已成功拉完约 150MB（含 `tomcat-embed-core` ~3.5MB 等 MB 级 jar）。若链路存在 512KB 硬上限，那些早已失败 → 判定为**瞬时传输截断（约 80%）**。
- **判定 `-Dmaven.test.skip=true` 无效**：Maven 依赖解析由 mojo 描述符的 `requiresDependencyResolution` 驱动，**发生在 mojo 执行体之前**；`skip` / `maven.test.skip` 是 mojo **内部**参数，解析之后才被判断 → 省 test 编译与执行，**省不掉 test 依赖下载**。
- 给出**日志格式旁证**：报错 `Failed to execute goal on project nexus-start: Could not resolve dependencies` **不带 goal 坐标**，正是执行前预解析包装器的格式（真正的 mojo 失败会写完整插件坐标）。
- **顺带确认一个好消息**：该错误针对 **jar 而非 pom**，说明 `nexus-start` 的**主代码已编译通过**，只是卡在最后的依赖解析。
- 推荐组合：① 重跑看**数字指纹** → ② 给 Dockerfile 加**构建层重试循环**（唯一对"读 body 中途截断"有效的层级）→ ③ 仅当指纹复现才考虑传输实现切换/第二候选源。**明确不建议**改 `-Dmaven.test.skip=true`，**不建议**动 POM。
- 论证了为何 `-Dmaven.wagon.http.retryHandler.count` 结构上无用：重试处理器包在**请求外层**，而该异常是**读响应体时**才抛出（请求早已成功返回），**天然逃逸重试**；且 Maven 3.9.x 默认传输已可能不是 wagon。
- 全程未执行任何 docker / mvn 命令，未改任何文件。

## 遇到的坑

- **主会话的"整数边界 = 确定性"推理是错的**：对**缓冲式 I/O** 的字节计数，整数倍是**必然结果**而非异常信号。从"数字很整"推出"存在固定分片/上限"，是本次的核心误判。
- **依赖解析与 mojo 执行的先后顺序**容易被想当然：`skip*` 系列参数全部在解析之后生效，因此**任何 skip 参数都拦不住依赖下载失败**。
- **报错文本的格式本身就是信息**：`Failed to execute goal on project X`（无 goal 坐标）vs `Failed to execute goal <groupId>:<artifactId>:<version>:<goal>`（有坐标）—— 前者是**预解析阶段**失败，后者才是 mojo 内部失败。这个判据此前未被利用。
- **传输层重试的适用范围有结构性边界**：请求级重试无法覆盖**响应体读取阶段**的失败。想当然地加 `retryHandler.count` 会空转。
- **"源配好 ≠ 下载成功"**：本次阿里云源**完全正常**（报错行明确写 `from/to aliyun-central`），失败发生在传输环节。这补上了此前失败模式清单只覆盖"配置类错误"的缺口。

## 下次怎么改进

- **不要从"数字很整"推断确定性故障**。缓冲式 I/O 的字节计数天然是缓冲大小的整数倍（8K/64K 最常见）。要判定确定性，**看指纹能否复现**（同一 artifact + 完全相同的 expected/received），而不是看数字本身是否整齐。
- **读报错要读格式，不只读内容**：`Failed to execute goal on project` 与 `Failed to execute goal <坐标>` 是**两个不同阶段**的失败。把这条判据固化下来，能立刻定位是"预解析"还是"mojo 内部"。
- **提出失败模式时，按"配置层 / 传输层 / 语义层"三层并列**，不要只列配置层。本次失败恰好落在传输层，而此前清单漏了这一层。
- **重试要放在最外层能覆盖完整操作的地方**（构建层循环），而不是依赖组件内部的重试机制 —— 后者的作用域常常不覆盖实际出错阶段。
- **"能不能用某个参数绕过"要先问"该参数在生命周期的哪一步生效"**：`-DskipTests` 与 `-Dmaven.test.skip=true` 的差别正是活教材 —— 二者都绕不过**解析早于执行**这一事实。
