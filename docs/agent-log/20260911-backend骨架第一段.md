## 遇到的坑

- **`maxTurns: 40` 严重不够**：任务实际需要建 20+ 个文件（6 个 POM + 各模块源码 + 配置 + API 文档），40 轮在写完 POM 和 common 模块后就耗尽。**停止是静默的** —— 没有报错，只返回一句进行中的话（"Now the `nexus-common` module — the zero-dependency base."），主会话若不主动查磁盘，会误以为任务正常完成。
- **失败模式是"交付物残缺但不报错"**：这是最危险的形态 —— 比直接报错更难发现，需要主会话主动 `find backend -type f` 核对文件树才能识破。
- **历史同类证据**：此前 devops-engineer 那次诊断任务 `tool_uses: 50`、`maxTurns: 50`，同样卡着上限停住（当时被用户手动 kill，未察觉是上限所致）。说明 `maxTurns` 偏低是**全项目 agent 的共性问题**，不是个例。
- **续跑代价**：续跑要求 agent 重读上下文才能定位缺口，比一次跑完更烧 token —— 设置过低的 `maxTurns` 表面省成本，实际更贵。

## 下次怎么改进

- **提高各 agent 的 `maxTurns`**：`backend-engineer` 40 → 80~100、`frontend-engineer` 35 → 80、`devops-engineer` 50 → 80。判定依据是**任务要产出的文件数/步骤数**，不是凭感觉。骨架类任务（多文件、多目录）尤其需要放宽。
- **主会话在 agent 返回后必须核对产物**，不能只看文字汇报：`find <目标目录> -type f | wc -l` 对一下预期文件数，是识破"静默截断"最快的手段。
- **派活时明确告知"撞上限时优先保哪些交付物"**：本次已在下发时排了优先级（`nexus-start` > `docs/api/` > 其余），续跑时可直接从缺口接上，不必重新决策。这个做法有效，应沿用。
- **拆小任务粒度**：一个 agent 调用里塞"6 个 POM + 5 个模块源码 + API 文档"本身就偏大。按模块拆成多次调用，每次都在轮次预算内，且失败时损失面更小。
