## 做了什么

- 论证**必须先重建 builder**，机制讲得准确：`nexus-backend` 的 stage 1 是 `FROM nexus-builder:dev`，buildx 只查**本地镜像库的该 tag**，不会看 compose 里 `builder` 服务的 Dockerfile。且钉子扎在"**tag 存在但陈旧**"这种更隐蔽的情形 —— 不报错、静默用旧镜像 → Maven 找不到 `/root/.m2/settings.xml` → 回落境外源。
- 给出三项验收判据，**判据设计合理**：
  - A. 日志里 `Downloading from aliyun-central` 计数 > 0 且 `Downloading from central:` = 0；并正确指出**该判据只对首构有效**（cache mount 跨构建持久化，二构无 `Downloading` 行**不是**失败）。
  - B. `nexus-start/target/` 唯一 jar：论证"**构建成功本身就是证明**"（COPY 通配命中 0 个或 ≥2 个都会让构建红掉），无须额外验；`*.jar.original` 不命中通配无害。
  - C. 运行镜像不含工具链：给出体积量级判据（backend 100-150MB 档 vs builder GB 档）+ `command -v mvn node npm psql` 应全无输出 + `docker history` 分层判据，并提示 containerd image store 下 history 可能不全、以体积为准。
- 列出 7 条失败模式（按可能性排序）并给报错指纹与处置，其中**第 7 条最有价值**：`@project.version@` 未被资源过滤替换 —— **构建全绿但结果是错的**，属隐性故障，只有靠运行时 `data.version` 是否为字面量才能发现。
- 给出构建后的验证与 503 场景造法（`docker compose stop redis` → 预期 503 + `code:20000` + `checks.redis:DOWN`）。

## 遇到的坑（含本报告自身的错误）

- **报告自身的错误一：`--profile build` 并非必需**。报告实测 `docker compose build --print builder` 不报错，**显式点名服务本身就会激活其 profile**。这与前一份报告的结论相反，且**我此前已把错误结论写进了 `docs/design/00-环境与部署.md` §4.3**（"不激活 profile 会报 `no such service: builder`"），需要回改。
- **报告自身的错误二：对 `build nexus-frontend` 连带构建的解释不成立**。报告称"之前 frontend 连带构建的观感，来源应是没写服务名"，但用户当时的命令**明确写了 `nexus-frontend`**。我事后用 `build --print` 复核确认：`nexus-frontend` 的 targets **确实含 `nexus-backend`**（因 `depends_on`），而 `nexus-backend` 的 targets 只有它自己。**前一份报告的解释才是对的。**
- **未预见实际失败模式**：报告把"Maven 走境外源"列为第 1 失败模式，但实际失败是**源已生效、传输被截断**（`Premature end of Content-Length delimited message body`，expected 586,031 / received 524,288 = 恰好 512KB）。这说明失败模式清单**覆盖了配置类错误，却漏掉了传输类错误**。
- **同源两个子代理给出互相矛盾的结论**：两次独立的 devops 任务对同一现象（`build <service>` 是否连带构建）给出了相反解释。**若不做交叉验证，会采信后到的那份、得到错误结论。**
- **报告的时效性问题**：任务派出于事件发生前，返回于事件发生后。报告本身质量不低，但其"下一步"部分已失效 —— 若不核对时序，容易把过期结论当现状。

## 下次怎么改进

- **同一事实被两个子代理给出相反结论时，必须用一条只读命令自行裁定**，不能采信"更晚返回的那份"。本次用 `docker compose build --print <service>` 一条命令即裁定完毕，成本极低。**这是本次最重要的教训。**
- **派活时应把"已发生的关键事件"一并写进 brief**：本次派单时构建失败尚未发生，导致报告与现状错位。若能及时补充，可省一次往返。
- **失败模式清单要覆盖"配置正确但传输失败"这一类**：源配好 ≠ 下载成功。应把 `Premature end of Content-Length delimited message body`、`Connect timed out`、`Read timed out` 等传输层错误与配置层错误**并列**列出，并给出重试与重试参数两条路径。
- **"构建成功=验收通过"只在 COPY 通配这类"失败必红"的场景成立**；对 `@project.version@` 这类**静默错误必须显式验证**。区分这两类，能省掉不必要的验证步骤，同时不放过隐性故障。
- **子代理写进项目文件的结论需与原始实测证据对账**：我此前把"不激活 profile 会报错"写入设计文档，实为未经验证的转述。**转述结论入文档前应先复核。**
