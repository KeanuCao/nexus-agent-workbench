## 遇到的坑

1. ★ **判据"答案与资料一致"不成立 —— 根因是召回，不是链路**。
   现象：问「去年利润是多少」→ `grounded=true`、`sources` 5 条非空，但 `answer="知识库中未找到相关内容。"`，
   3 次复现一致。**排除过程（全是实测，无一条靠推断）**：
   - 不是前缀不对称：`cos(库内存储向量, embed('search_document: '+原文)) = 1.000000`；
   - 不是生成坏了：换问「受益计划的平均服务年限」→ 答"27.4 年"且与 chunk 369 原文一致（`score=0.7952`）
     ⇒ 检索→生成整条链路是通的；
   - 不是解析：`84.1 亿元`（2 处）与 `8,408,057 千元`（财报形态）都在正文里，Tika 抽出 263,910 字；
   - 不是阈值筛掉：**反了** —— 阈值 0.5 一条都没筛掉，5 条无关块拿 0.71~0.75 分。
   **定量结论**：含答案的块在 587 块中排 **第 27 名**（问"归母净利润"第 47 名、"营业总收入"第 10 名），
   而完全无关问题的 top1 就有 **0.6929** ⇒ `(S_miss+S_hit)/2 ≈ 0.72` 这种标定**救不了**。
   **教训**：① "三道闸工作正常"（模型如实说不知道）与"资料被送上去"是**两件事** —— 前者成立会掩盖后者失败；
   ② 语料相关的验收标准（"能准确回答"）应当**在写 TC 之前**先测一轮排名，否则它会在最后一刻才暴露成不成立；
   ③ 平面化的相似度分布（无关块 0.71~0.75）是**该换 embedding 的信号**，不是"调阈值"的信号。
2. **我（主会话）留在沙箱脚本里的注释是过时的**：B3 那行写着"阈值进 WHERE 期望用不上索引"，
   而实测仍是 `Index Scan + Filter` ⇒ 执行者按注释预期去看，会以为脚本坏了。
   处理：设计稿、补丁注释与 TC-03 已按实测订正；`.tmp/` 下的脚本属一次性产物，不再维护。
   **教训**：脚本里的注释也是**断言**，订正结论时要连它一起 grep 到。
3. **生产 SQL 的规划器取舍**（附带观察，供决策）：带 tenant JOIN + score 列的真实检索语句，在 587 行时
   规划器选 `Bitmap Index Scan(idx_kb_chunk_tenant_id) → Hash Join → Sort`（cost 119 vs HNSW 761），
   **关了 seqscan 也不走 HNSW**。小表下这是正确取舍；量级上去后它会变成"全租户扫描 + 排序"的隐患 ⇒ 记 backlog。
4. **一处没做成的核对**：想用 `od -c` 对 SSE 帧做**字节级**核对（看 `event:` 后有无空格），被权限拒绝。
   捕获显示是 `event:meta`（无空格），且 `frontend/src/utils/sse.ts` 显式兼容两种写法 ⇒ 判定为非问题，
   但**字节级确证没做**（如实记录，不当作已验）。
5. 它顺手 commit 了自己的 agent-memory（`84ec84a`，未 push）—— 与"push 归用户"的约定一致，无冲突。
