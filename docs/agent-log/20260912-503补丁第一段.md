## 做了什么

目标：修复一个已确认的契约缺口 —— 后端在 503 降级时返回**完整的 `data`**，但前端拦截器的错误分支把 `data` 丢弃，导致**降级时看不到是哪个依赖 DOWN**（而这恰是"真实探活、不造假"最该被展示的时刻）。

已落盘的核心改动：

- **`frontend/src/api/request.ts`（202 行）**：`BusinessError` 扩展为携带 **`data`** 与 **HTTP status**（原实现只有 `code` / `msg`）。错误分支把 `data` 一并封入，并写明理由：

  > `// 这里必须把 data 一并封进 BusinessError：msg 只说明"依赖服务不可用：redis"，`
  > `// 而"每个依赖各自 UP/DOWN"只存在于 data.checks 里，丢了 data 就无法逐项标红。`

- **`frontend/src/api/health.ts`（57 行）** 与 **`components/HealthCheckPanel.vue`（148 行）**：消费新增的 `data`，支持逐项渲染 UP/DOWN。
- 文件头注释补上了判据来源指引（`docs/api/README.md §2.3 / §4.2.1`），并注明"失败时 data 可能为 null，也可能仍有完整数据"。

**撞限时正在做**：统一"失败 → 文案"的映射（网络失败时面板显示 axios 英文原文、而 toast 显示中文，两处不一致）。

## 遇到的坑

- **`maxTurns: 35` 撞限（该 agent 第二次撞限）**：上一次是前端骨架任务（`tool_uses` 52）。两次都是**卡在收尾**，且**停止是静默的** —— 只返回一句进行中的话，必须主动查磁盘才能确认核心改动其实已经落盘。
- **墙钟耗时严重误导成本判断**：`duration_ms` 显示 94 分钟，看起来是个巨型任务；实际 `tool_uses` 48、token 7.2 万，与其它 5~9 分钟的任务同量级。**agent 在等待用户输入期间墙钟持续累积。** 若据此判断"这个 agent 太慢/太贵"，结论会是错的。
- **收尾阶段的打磨工作吃掉了剩余轮次**：核心修复早已完成，最后消耗在"统一文案映射"这类一致性收尾上。这类工作**价值真实但优先级低于"跑验证 + 出汇报"** —— 尤其本任务唯一的高价值验证手段（`npm run type-check`）上一次因禁 build 而从未跑过，本次又被排在了打磨之后。
- **契约缺口的成因值得记录**：后端 `HealthController` 用 `Result.failure(code, msg, report)` **保留了完整 data**（设计正确），但前端拦截器按"非 2xx 走错误分支、只取 msg"处理，**两边的合理性叠加出了缺口**。没有一个环节是错的，缺口出在**交接面**。

## 下次怎么改进

- **把"跑验证 + 出汇报"的优先级提到任何打磨工作之前**。本任务的正确顺序是：核心修复 → `npm run type-check` → 汇报 → （剩余轮次才做）文案统一。**验证未跑等于交付未完成，而文案不一致只是瑕疵。**
- **评估 agent 成本用 `tool_uses` / `tokens`，不用 `duration_ms`**。后者混入了等待用户输入的空闲时间，会把 5 分钟量级的任务显示成 94 分钟。
- **跨端契约要专门检查"交接面"**：两端各自都合理，缺口仍可能出现。本次即典型 —— 后端"失败也返回完整 data"合理，前端"非 2xx 走错误分支"也合理，但合起来就是数据丢失。**审查契约时应问："这个字段在失败路径上会不会被某一端丢掉？"**
- **禁用 build 类红线时必须同时指定替代验证手段**（本项目已第二次遇到）：上次是 `npm run type-check` 没跑，这次又被排到最后。派活时应**把替代验证写成明确的验收项**，而不是"可以跑"。
