## 做了什么

1. **两个 provider**：`OllamaService`（NDJSON 逐行解析）、`DeepSeekService`（OpenAI 风格 SSE，`data:` + `[DONE]`；**无密钥即 20100，不发无谓网络请求**）。另抽 `UpstreamChatRequest` 共用上行请求体（两家形状本设计 §4.3 里就一致），但**行协议仍完全各自实现**。
2. **编排**：`ChatService`（端口 + `CallerContext`）、`ChatServiceImpl`、`ChatStreamSession`（★ 把单条流的状态机从 service 拆出，三条不变量——**meta 唯一 / 终态唯一 / 断开即取消**——集中一处）、`ChatController`。
3. **★ 闭合第一段交出的三个缺口**：
   - **池满 503**：`GlobalExceptionHandler` 加 `TaskRejectedException` 出口 → `503` + `20100`。已从源码确认 `ThreadPoolTaskExecutor.execute()` 会把 `RejectedExecutionException` 包成 `TaskRejectedException`。`ChatServiceImpl` **刻意不 catch**，让异常 message 自带的 `pool size / active threads / queued tasks` 穿到处理器。
   - **软上限定时器**：`AsyncConfig` 加单线程 `ThreadPoolTaskScheduler`（daemon + `DisposableBean` 自动关闭）+ `ChatServiceImpl.scheduleSoftTimeout()`；构造期 warn 校验 `soft < stream`，`finally` 里 `cancel(false)`。
   - **D10 透传**：`ChatController` 在**请求线程**抓 `CallerContext`，`ChatServiceImpl.runStream` 起始 `set`、`finally` `clear`；并有单测**直接断言工作线程上读到的 userId/tenantId**。
4. **闭合前端报的契约缺口 G1**：`openapi.yaml` 补 `ChatStreamDelta`（`required: [content]`，注明增量非累积）、`servedBy` 由紧 enum **放宽为 `string`**（理由同前端：§10.1 预告自动路由会上 `fallback`，展示字段不值得让页面打不开）；两处各写"帧表 ↔ schema"对应关系。

## 遇到的坑

1. **★★ 设计文档 D1 指定的 API 在 Spring 6.1 里不存在。**
   D1 写的是 `execute(requestCallback, responseExtractor)` —— 那是 **`RestTemplate`** 的 API，`RestClient` **没有**它。它唯一的原始响应入口是 `exchange(ExchangeFunction)`。
   → 处理：改用 `exchange`，**在回调内部读完**，安全性质与原意完全一致；**未自行改设计文档**，而是回抛给架构确认（主会话已据此订正 D1 并记入 §12）。
   **★ 这次能核实，正是因为 `.deps-src/spring-6.1.21/` 已铺好** —— 主会话在同一时间做的这件事，直接让这个错误在编码阶段而非联调阶段被发现。
2. **★★ D1 的担忧被源码级证实，且比原判断更严重。**
   原判断是"回调返回后响应**可能**已被关闭"（标为待实测）。核实后：
   - `DefaultRestClient.exchangeInternal` 在回调返回后的 `finally` 里才 `close()`；
   - 而 `SimpleClientHttpResponse.close()` 会调 **`StreamUtils.drain(responseStream)`** —— **把剩余响应读空再关**。
   → 所以回调之后再读不是"可能失效"，而是**必定读到一条已被 drain 到 EOF 的流**。**症状是"一个字都没有"，而不是"分片不连续"** —— 后者会被误判成"上游没返回"，排查方向完全不同。这一条把风险 3 的一半从"待实测"升级为"已核实并规避"。
3. **契约文档 §6.3 与 §6.2 自相矛盾**（它自行订正并记录）：§6.3 把"上游中途报错 / 服务端软上限截断"并列写成 `error` 帧 `20100`，而 §6.2 规定软上限截断是 `done` + `finishReason=timeout`。按 §6.2 实现，**拆开了那一格**。
4. **"meta 必有"与失败路径冲突**（澄清并补文档）：若上游一个字都没吐就失败，这条流**只有一帧 `error`**，没有 meta。已在 README §6.2 与 openapi 的 `ChatStreamMeta` 各加一句：**前端不要断言"第一帧一定是 meta"**（否则"上游不可用"会变成前端解析异常）。
5. **第一段"本段不需要改 pom"不成立**：provider 直接 import `ObjectMapper`/`JsonNode`，需补 `jackson-databind`（按本项目"自己 import 的自己声明"的取舍）。
6. **设计 §4.1 的文件清单缺 3 个类**：`ChatStreamDelta`（delta 载荷 DTO）、`UpstreamChatRequest`、`ChatStreamSession`。均属清单缺口、非语义冲突，已逐一说明由来。
7. **无法编译验证**（同第一段）：宿主无 `mvn`/`javac`，且它是本段**唯一无法自证的一环** → 明确列出 7 条请 devops 重点验证的项，含 lambda 目标类型、`SseEmitter` 各方法可见性、`TaskRejectedException` 可达性、37 条单测能否编译跑过。

## 下次怎么改进

1. **★ 写"必须使用某框架 API"时，先去源码里确认那个方法真的存在。**
   本次 D1 的错误根因是**凭记忆写 API 名** —— `execute(requestCallback, responseExtractor)` 是 `RestTemplate` 的经典签名，很容易被"顺"到 `RestClient` 上（两者同族、命名相近）。
   判据：**设计文档里出现具体方法签名时，要么附源码路径、要么标"待核实"** —— 不能写得像已确认。
   配套：`.deps-src/` 这类"把第三方源码放进工作目录"的做法**要早做** —— 它把"核实成本"从"起容器/翻 jar"降到"Grep 一下"，本次直接因此拦住了一个会活到联调阶段的错误。
2. **"响应流还在不在"与"是否增量到达"是两个独立问题，要分开验证、分开表述。**
   设计原文把两者混在一条"待实测"里。核实后才发现：前者是**确定的**（被 drain）、后者才是待实测。
   判据：**同一条风险里若含两个可独立为真/假的性质，拆成两条** —— 否则会出现"验了一半就以为全验了"。
3. **把状态机从 service 里拆出来，是这类流式实现的默认做法。**
   `ChatStreamSession` 集中了三条不变量（meta 唯一 / 终态唯一 / 断开即取消），使它们**只在一处可被违反**。这三条恰好也是设计文档反复强调、且最容易在分支里漏掉的。
   判据：**一条流有 ≥3 条"全局唯一/互斥"约束时，就该有独立的会话对象承载它们。**
4. **契约里出现"必有 X"这类断言时，必须同时回答"失败路径下还成立吗"。**
   本次"meta 必有"就没覆盖"上游一个字没吐就失败"的情形 —— 而那条路径**恰好是错误处理最常走的路**。
   判据：**凡是"必有/唯一/一定"，都要配一句失败路径下的行为**。
5. **拆段交接时，"上一段说的不需要改 X"要当作待验证项而不是结论。**
   第一段判断"本段不需要改 pom"，第二段发现要加 `jackson-databind`。这不是第一段错 —— 而是**当时还不知道会怎么实现**。判据：**交接里凡是关于"未来那段"的判断，标注为预判、不要写成事实。**
