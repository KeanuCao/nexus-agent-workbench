## 遇到的坑

1. ★ **草稿里的「务实兜底」与项目红线正面冲突，且冲突面比看上去具体。** 草稿第 10 条
   「如果冲突，就复用 nexus-agent-workbench 里面的测试环境」—— 听着是省资源的折中，实则部署与测试会写
   **生产环境的容器、业务库与 Redis**（登录本身就会写一个 Redis token 键），与 `qa-engineer` charter 的
   《Test Harmlessness》直接冲突。处置：不代拍，落成 M4-⑤ + 待确认第 5 条（选项 + 推荐"不允许"）。
2. ★ **草稿把"现有脚本能做到 X"当既成事实，静态核对才发现缺口。** 草稿 17 要「拉取 github 上 PR 的代码」，
   但 `deploy.py` 的 `git-sync` 只认分支（`NEXUS_REPO_BRANCH`）、**没有 ref/SHA 入参** ——
   这是本阶段最硬的实现缺口，草稿完全没有意识到。处置：单列为首要风险，先定方案再谈 5.1/5.2。
3. **「优先 Role」的定位口径在表单控件上不成立。** 草稿 13 要求「pytest 脚本优先使用 Role 结合 tid」，
   但 `<input type="password">` 在可访问性树里通常没有 textbox 角色（推断，未实测）。处置：口径收窄为
   「按钮/链接/标题用 Role，表单控件一律走定位属性」，并把「密码框 Role 定位」列入需实测清单。
4. **作战地图的进度行滞后于实况，照它推断当前进度会得出错误结论。** `docs/核心任务.md` 第 50/92 行与
   `docs/task/task.4+RAG知识库.md` 仍写阶段3「待开始」，而 `docs/agent-log/` 已有 2026-09-22 的阶段3
   实施与端到端验收留档、`TC-03.md` 也已存在。处置：**只报告、不修改**（那是用户逐项验收的地盘），
   真实进度由「进度行 + agent-log 日期 + TC 文件」三者交叉核对得出。
5. **阶段编号是混用命名的，不能直推。** 既有写法为「阶段0 / 第一阶段 / … / 第四阶段」，本阶段只能**推定**为
   第五阶段 → `task.6` → `TC-05`（TC-04 按编号约定仍归未开工的阶段4）。处置：文件按推定写，推定项单列待拍板。
