## 遇到的坑

1. ★ **"重建成功"不是判据，"内容是否变了"才是。** 前端镜像重建（§6.5 第 5.5 步）被**镜像源故障**挡下
   （`docker.m.daocloud.io` DNS 超时 / TLS 握手超时，BuildKit 与 legacy builder 症状不同；
   WSL 宿主侧 `getent hosts` 同样 unresolved ⇒ 网络窗口，不是本机配置）。处置：**先判这一步是不是内容中立** ——
   容器内 `/etc/nginx/conf.d/default.conf` 与宿主源码 **sha256 逐字节相同**（含 `client_max_body_size 12m`），
   且本项目 **dist 是卷挂载、逐请求读取** ⇒ 该偏差**不影响功能**；那次 131.9 s 的上传本身就是通路证明。
   ⇒ 教训：能把"操作成功"换成"结果等价"来判的，就别死等操作成功 —— 但**必须留下等价性的证据**（sha256 + 镜像 id + 挂载方式）。
2. **实测数字推翻了设计里的估算**：设计的"嵌入 2.1 s/批 ⇒ 本夹具 80~90 秒"是**宿主直连 Ollama** 的估算，
   端到端实测 **131.9 s（≈3.6 s/批）**，偏慢 1.5 倍。⇒ 已由主会话订正设计 3 处 + 定案"耗时只当参考值、不当硬判据"，
   TC-03 由 qa-engineer 同步改。**设计里的耗时数字必须标清"在什么路径上量的"**（直连 vs 经 nginx）。
3. **"验产物是新的"要有硬标记**：本次用 **jar 内的类文件字符串 + 8088 抓到的 JS 片段**，
   而不是 mtime 或"构建成功"。（builder 镜像里**没有 `unzip`**，抽类文件要用 JDK 的 `jar xf`。）
4. **复现了已知的 stdin 争用**：`heredoc 喂 bash -s` + 脚本里再套 `docker exec -i` ⇒ 第二次 exec 起输出整体丢失。
   落盘执行后零故障（`wsl.abc.md` §3.8 已记，本次是同一形态的第 N 次复现）。
5. **`.env` 里根本没有 `NEXUS_REPO_*` 那三行** —— 值来自 compose 的 `${NEXUS_REPO_BRANCH:-main}` 默认。
   "配置在哪"这件事也要**实证**，别按记忆去找。

## 下次怎么改进

1. **部署类任务的判据写成三段**（本次已是这个形态，建议固化为模板）：
   ① **输入对不对**（拉到的 SHA / 用到的分支）；② **产物换了没**（标记物：类文件字符串、前端 JS 片段、镜像 id）；
   ③ **行为对不对**（HTTP 状态码 + 响应体 + 日志行）。**任何一段缺失，"通过"都不成立** ——
   本项目已经出现过"陈旧容器状态被读成新证据"（换 bge-m3 那次）。
2. **操作类步骤失败时，先问"这一步的产物是否已在别处等价存在"**，再决定是否重试或死等；
   等价性必须可核（sha256 / 内容 diff / 挂载方式），否则不算数。
3. **耗时数字一律标注"在哪条路径上、什么负载下"量的**；演示/判据只用它做参考值，
   硬判据只留"必须小于前端超时"这类**与架构决策同源**的界限。
