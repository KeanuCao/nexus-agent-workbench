## 做了什么

1. **耗时判据改成"只记实测值 + 一条宽松上界 `< 300 秒`"**，并写明**为什么是 300** ——
   它与前端逐请求上传超时 `UPLOAD_TIMEOUT_MS = 300_000` **同源**（设计 §5.1-4/§6.1）。
   超过它前端先超时、用户看到"失败"而服务端其实已入库 —— 这才是这个数字有意义的地方。
   两个被删掉的窗口（`120~140 秒` 与本文件曾引的 `80~90 秒`）**留在文档里当反面证据**，不是删了事。
2. **结果判据一个没松**：`fileSize=1682689`、`charCount` 25 万~28 万、`chunkCount` 585~590、
   `chunkCount < 3000`（不撞 `10204`）、`batches=37` 全部原样保留 —— **放松的是时间，不是结果**。
3. **脚本侧**（`qa/scripts/tc03-kb.sh`）：新增 `TC03_MAX_SECONDS`（默认 **600**）用于 `curl --max-time`；
   文档写明它**只防无限等、不是判据**，故意留 **2 倍余量**以免脚本先于前端放弃。
4. **顺手订正 5 处"文档与现实打架"的旧断言**（均有只读探针证据、**保留历史实测不改写**）：
   ① nginx 1MB 墙（5 处写"走 8088 传 1.68MB 必然 413"，现实 200 ⇒ 标"已修 + 复测证据"，实测栏留白）；
   ② `§0.2` 前置状态块三条现已满足；③ `§0.2` ① 的命令本身跑不起来（仓库根无 compose 文件 ⇒ 补 `cd`）；
   ④ `§5` 前端前置不再成立（`kb.ts` 已存在、`KnowledgeView` 已是真页面）；⑤ `3.1-2` 说重放两份补丁、实际三份。
5. **无害性自证**：全程零写操作（`psql SELECT` / `logs` / `ls` / `grep` + 一条**免 token** 探针 → 401 写不进库），

## 遇到的坑

1. ★ **"改一处判据"的活，撞上了同一份文档里 5 处已被现实取代的断言。**
   处置（值得固化）：**保留历史实测 + 加带日期的订正 + 在报告里单独列出并声明"超出字面范围、可回退"** ——
   既没有静默挑一条照做，也没有改写历史。这正是本项目"指出矛盾 ≠ 可以停工"的落地形态。
2. ★ **同类判据第二次栽在同一件事上**：上次是"答案内容用精确串"、这次是"耗时窗口" ——
   凡判据里含**随机器漂移的量**（耗时 / 负载 / CPU）都会假失败。本项目**无 GPU、向量化走 Ollama CPU 推理**，
   同一台机器上 **2.1 → 3.6 s/批（约 1.5×）** 的漂移就是现成证据。
3. **测试脚本自己的超时不能早于被测链路的最外层超时**：`curl --max-time` 若比前端 300s 更紧，
   会把"用户其实能成功"记成**退出码 28**，再被误读成"上传失败" —— 脚本自己制造假失败。
4. **它报的"设计稿 1251 行仍未改"是读取时的快照**（主会话已先改掉）：跨会话协作里"我看到的"与"现状"会不同步。
   它**只报不改**（属别人的文件）是正确的边界；由主会话核对后判定，本次核对结论是"无需改"。
5. **文档里的"前置条件"也要当假设验收**：`§0.2` 的前置块已过期，且其中一条命令（`cd 仓库根 && docker compose logs`）
   **本身就跑不起来** —— 仓库根没有 compose 文件。过期前置会把"能跑"误报成"跑不了"，反之亦然。

## 下次怎么改进

1. **派"改判据"类的活时，把这条写进要求**：若发现同一文档里有与现实冲突的其它断言 ⇒
   **保留历史、加日期订正、并在报告里单独列出**（本次执行者自发这么做，效果好，建议固化为模板）。
2. **判据里禁止出现随机器漂移的量**；必须记录时写成"实测记录值"，并把**唯一的硬上界挂在架构决策上**
   （这里是"前端 300s 超时"）。上界与决策同源，判据才既有意义又不会假失败。
3. **测试脚本的超时要晚于被测链路的最外层超时**（本例：脚本 600s > 前端 300s），
   并在注释里写明"这不是判据" —— 否则脚本自己会制造假失败。
