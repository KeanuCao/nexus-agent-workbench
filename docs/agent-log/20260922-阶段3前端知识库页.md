# 阶段3 前端实施（3.5 知识库页面：`KnowledgeView.vue` + `api/kb.ts`）

- **Agent**：frontend-engineer ｜ **耗时**：约 5 分钟（撞 35 轮上限，被 Resume 后交回报） ｜ **task-id**：无（本段由主会话手工留档）
- **产物**：`frontend/src/api/kb.ts`（226 行）+ `frontend/src/views/KnowledgeView.vue`（562 行，重写占位页）；`npm run type-check` **exit 0**（主会话独立复跑确认）

## 做了什么

1. **`api/kb.ts`**：四个函数全走 `request.ts` 的 `request<T>()`（不自己解 `Result`、不碰 axios 配置）；
   逐请求超时 `UPLOAD_TIMEOUT_MS = 300_000` / `ASK_TIMEOUT_MS = 120_000`；上传用 `FormData` 且字段名写死
   `file`、**刻意不带任何 headers**（注释说明这是"不给 axios 添乱"）；7 个 wire 类型逐字段注明契约出处。
2. **`KnowledgeView.vue`**：顶部边界 `el-alert`；上传走 `:http-request`（**唯一不走 EP 自带 XHR 的写法**）
   + 进度文案/禁用 + 成功"已入库 N 段"并刷新列表；表格 + `el-popconfirm`（文案含"无法恢复"）；
   问答走 textarea + 回车提交（IME 组合态放行）；`grounded=true` → 答案 + `el-collapse` 引用
   （`文件名 · 第 N 段(chunkIndex+1) · 相似度 x.xx`）、`grounded=false` → `el-alert type="info"` 展示后端文案
   且**不渲染引用卡片**；答案与引用一律 `{{ }}` 插值 + `pre-wrap`。
3. **两处"文档打架"按更忠实的一条做并上报**（详见「遇到的坑」1、2）。
4. 三处按设计意图但换了写法（都给了理由）：不手工调 `onSuccess/onError`（EP 对返回 Promise 的 handler
   会自动接）、`@keydown` 而非 `@keyup.enter`（keyup 时换行已插进输入框，且 keydown 才能放行 IME）、
   补了 `createdAt` 倒序（契约 §7.2 明写"排序未约定，前端需自行排序"）。

## 遇到的坑

1. **契约与设计的超时值打架（120s vs 300s，我造成的）**：契约 §7.1 写着"设计 §5 给的 **120s**"，
   而设计 §5.1-4 在沙箱实测后已改成 **300_000**（587 块 ≈ 80~90 秒，120s 只剩 ~30s 余量）。
   子代理按 300s 实现并上报，主会话回头把契约那句改成 300s。
   **教训**：改了设计里的取值，要**顺手 grep 全仓有没有别处引用过它** —— 同一晚我已经两次栽在这类漂移上。
2. **设计内部不一致**：§5 的文件表写 `uploadDocument(file, onProgress?)`，同节签名块写 `uploadDocument(file: File)`，
   而 §5.2 也没有百分比 UI。子代理按签名块实现（无进度回调）并上报，主会话订正文件表。
3. **`el-upload` 的 `handleExceed` 少一句 `submit()` 就静默不上传**（读 EP 2.14.5 源码得出，非猜测）：
   `handleStart` 只往列表加一条 `status='ready'`，**不发请求**；真正发请求的只有 change 事件与 `submit()`。
   按 EP 文档示例写（`clearFiles + handleStart`）的表现是：文件出现在列表里、状态永远 ready、
   **永远不上传，且控制台与网络面板都无报错**。已在注释里标"这句不能省"。
4. **`resolveHttpStatus` 与反代超时的联动**：上传 80~90s，若反代 `proxy_read_timeout` 是默认 60s，
   请求会死在代理层（**504 + HTML 错误页，不是 `Result`**）—— 那时 `resolveHttpStatus` **非 null**，
   页面会按"后端已应答"处理，显示成"响应体不是统一的 Result 结构"，**指向错误方向**。
   现场核对：本项目 nginx 的 `proxy_read_timeout` 已是 **300s**（阶段2 为 SSE 配的）✅ ⇒ 不触发。
   另外它给"超时 ≠ 失败"加了一道实用闸门：文案改成契约原文 + **自动刷新一次列表**（用户立刻看到"其实入库成功了"）。
5. **两个反直觉的"改坏方式"**（都写进了注释）：① 在 `kb.ts` 里补一条 `Content-Type: multipart/form-data`
   ⇒ 丢掉 boundary ⇒ `40001`；② 把 `:http-request` 换成 `action` ⇒ 401 不跳登录页、`Result` 不解包。
6. **又一次撞轮次上限**（本次 35 轮，比 qa 的 100 轮紧得多）：产物全在盘上、却零回报 ⇒
   主会话只能自己跑 `type-check` + grep `v-html`/超时常量来反推它做了什么。
   **两个 agent 同一晚撞上限，"写完一组就回报一次"应升级为子代理纪律。**

## 下次怎么改进

1. **改设计里的任何"取值"（超时、阈值、上限），立刻 grep 全仓引用**（契约、README、任务书、注释都算）；
   本晚 120s→300s 与 `allowed-extensions`、`embed-batch-size` 三处都是同一类漂移。
2. **前端涉第三方组件的"静默失败"要读源码确认调用点**：本次 `handleExceed` 那条若按文档示例写，
   会得到一个"文件在列表里、永远 ready、无任何报错"的形态 —— 这类坑只有读源码能提前发现。
3. **子代理纪律升级**：长任务分段交付（写完一组就回报），别把"产物落盘"当成交付。
4. **前后端文件严格分属**：本段子代理**没有** `git add` 别人的产物（当时 `qa/` 与 `docs/test-cases/` 还有
   未跟踪文件）—— 这条克制值得保留：提交按角色分批，由主会话统一收口。
