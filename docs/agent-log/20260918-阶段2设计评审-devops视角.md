## 做了什么

1. **先报了一条影响全局的前提**：Docker Desktop 当前未运行（`/usr/bin/docker` 软链目标不存在、`/mnt/wsl/` 下没有 cli-tools 挂载），**本轮所有「待实测」项现在闭合不了** → 因此只做静态核对与不依赖 docker 的最小复现，未启动任何容器。
2. 评审 §6 全节 + §8 验收表，产出 **1 个 🔴 + 3 个 🟡 + 5 个 🟢**，每条带文件:行号依据。
3. **反向核对并确认属实**：§6.0 的核心判断（镜像不含产物、后端镜像本任务无需重建）、三个反直觉点、`git check-ignore` 两条（自己复跑）、`env_file` 相对路径基准、`proxy_buffering off` 充分且无副作用、`up.sh` 无需改动、§6.7 契约落点。
4. 指出**一处举证强度不对等**：反直觉点①（`up -d` 是空操作）项目里有实测留档（`docs/design/00-环境与部署.md:439`）可引用；而反直觉点②（前端源码改动不用重启容器）**只有静态推断、无实测留档** → 按本项目纪律，②比①更该标「待实测确认」。

## 遇到的坑

1. **⚠️ §6.0 第 0 步「commit + push」不完整，会让第 3 步静默构建旧代码。**
   `git-sync` 执行的是 `git checkout --force --detach origin/${NEXUS_REPO_BRANCH}`，而 `.env` 里 `NEXUS_REPO_BRANCH=main`。**代码若在未合并的特性分支上被 push，第 2 步拉到的是 main（不含本任务代码），第 3 步照样 exit 0、日志正常、产物却是旧的** —— 正是 §6.0 整节想消灭的那类"改了没生效"。
   而且**当前仓库恰好就是这个形态**（`main=6965d58` 已合并阶段0、`stage0-env-and-skeleton=7a01af3` 未合并），不是假想。
   → 处理：给出改法（第 0 步补"确保提交在 `NEXUS_REPO_BRANCH` 上"，或临时改 `.env` 的分支名**并重建 builder 容器**——`restart` 不够，与反直觉点①同理），并把 `git-sync` 输出里 `[git-sync] 同步完成，当前提交：` 那一行**升格为判据**。
2. **第 7 步（验证密钥注入）的嵌套引号在 PowerShell 下不成立，且本机复现了内层变量读不到。**
   `wsl -d ... -- bash -c "…sh -c 'test -n \"\$DEEPSEEK_API_KEY\"…'"` —— **PowerShell 的转义符是反引号，`\"` 不是转义**，字符串会在第一个 `\"` 处断开。实测：同类写法经包装后内层变量读成空，而同环境 `printenv` 证明变量存在且长度正确。
   机制（哪一层吃掉了 `$`）**没定位到，按纪律标为未验证的推断**；但结果可复现，且**项目里早有同类留档**：`docs/agent-log/20260903-step2-manifest.md:10,15` 记过「`wsl -d … -- bash -c` 双层嵌套下 `$img` 展开丢失」，并已立规矩「经此包装的命令默认放弃内层变量」。
   → 处理：给出**完全不含 `$`** 的替代写法（`printenv DEEPSEEK_API_KEY | wc -c`，实测 `XX=sk-test` 输出 `8`）；并顺带提醒排查时别裸跑 `docker compose config`（会把 `.env.local` 的值原样打出来），`check-env.sh:296` 用的是 `--quiet`，安全。
3. **§6.2 的 YAML 块是节选，若被整块替换会删掉 `management` 块** —— 后果是 `/actuator/health` 不再暴露 → **后端容器 healthcheck 直接失效**。这与 §6 早先订正过的那次（nginx 整块替换会覆盖 `X-Real-IP`）是**同一类错误的第二次出现**：给了片段却没标注"勿整块替换"。
4. **§6.2「非敏感项只改 yml 默认值」的清单漏了本设计自己新引入的三个变量名**（`NEXUS_AI_DEFAULT_MODEL` / `OLLAMA_CHAT_MODEL` / `DEEPSEEK_CHAT_MODEL`）—— 它们同样不在 `nexus-backend.environment` 里，写进 `.env` 一样收不到。`NEXUS_AI_DEFAULT_MODEL` 尤其危险，因为"默认模型"正是 §11-5 让用户拍板的那一项，最可能被顺手去 `.env` 里改。
5. **§6.0 的「生效判定」栏答的是"要不要重启"，不是"产物真的重建了没"。** 本项目已实测过 `builder-m2` 持久卷**静默复用旧构件**，让"配置没生效"长得像"构建成功"（2026-09-15 版本漂移故障现场）。`build-backend` 脚本本身会打印 `[build-backend] 产物已就绪：` + `ls -lh`，可直接当判据 —— 但设计没引用它。

## 下次怎么改进

1. **写"改了怎么生效"这类流程时，判据必须落在"能被观测的输出行"上，而不是"我做了什么动作"。**
   本次 🔴 的根因就是：第 0 步写的是动作（commit + push），而真正决定成败的是**提交落在哪个分支**这个状态。判据应写成「`git-sync` 输出里的当前提交 == 我刚 push 的 commit」。
   判据：**凡"静默失败"风险高的步骤（构建、同步、注入），都要配一条"打印出来、能一眼比对"的判据行。**
2. **给 YAML/配置片段时，一律显式标注"节选，勿整块替换"并写明"其余键一个都不能动"。**
   这类错误本项目已犯两次（nginx 一次、yml 一次），两次都是"片段看起来自洽"所以没人警觉。**成本一行注释，收益是免得整块替换删掉 `management` 这种看不见的块。**
3. **新增了环境变量，就必须同时回答"它怎么进容器"。**
   本次漏掉的三个变量名说明：**"声明了 `nexus.xxx` 配置项"和"这个配置项在容器里能被覆盖"是两件事**，中间隔着 compose 的 `environment` / `env_file`。判据：设计里每出现一个 `${VAR:default}`，就问一句"这个 `VAR` 会在容器环境里存在吗"——不在就明确写"只能改 yml 默认值"。
4. **引用既有实测留档，比重新推断更有说服力；反过来，没有实测支撑的条目要如实降级。**
   本次我主动指出反直觉点①有留档可引、②没有 —— 这让主会话能区分"哪条已经是结论、哪条还只是推断"。**派评审时值得明确要求这个动作**：不只报问题，还要报"设计里哪条断言我找到了实测支撑、哪条没有"。
5. **评审开工前先确认"验证链路是否可用"（本次是 Docker Desktop 未运行）。**
   这条要**放在报告最前面**，因为它决定了后面所有"待实测"项的意义 —— 若链路不可用，报告应当明说"这些现在闭合不了"，而不是让读者以为它们随时可以验。
