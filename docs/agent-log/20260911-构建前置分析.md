## 做了什么

- 回答"builder 建好了下一步搞什么"，产出 8 步执行序列（清障 → 验工具链 → 补源重建 → 建前端 → 建后端 → 全栈冒烟 → 0.2 → 0.3）。
- **实测出 npm 侧已被 lock 兜住**：`frontend/package-lock.json` 的 **148/148 条 `resolved` 全部指向 `registry.npmmirror.com`**（`registry.npmjs.org` 出现 0 次），故容器内 `npm ci` 不会走境外源 —— **npm 侧无需补源**。
- **定位到真正的缺口在 Maven 侧**：无 lock 等价物，每次构建都从 `repo.maven.apache.org` 解析，首次 150MB+。

- 判定 **Node 版本漂移（Windows 24 vs builder 20）不构成风险**，依据是逐包核对 lock 里的 `engines`（vite 5.4.21 / rollup 4.63.1 / plugin-vue 5.2.4 均覆盖 Node 20）+ Linux 平台二进制齐全。
- 挖出两处文档 bug 与三处清理项（见下），并给出 0.2 的跨 Agent 分工建议（`PatchCli` → backend-engineer；`/db-patch` 挂载 + 迁移包装 → devops）。
- **全程只做静态核对，未执行任何 docker 命令、未改任何文件**，符合项目纪律。

## 遇到的坑

- **cache mount 遮蔽镜像层配置**（本次核心发现）：`--mount=type=cache` 挂到某路径时，该路径下**镜像原有内容全部不可见**。这意味着"在 builder 镜像里 COPY 一份 settings.xml"这个看起来天经地义的做法**会完全失效且不报错**。同类陷阱适用于任何"往镜像拷配置、但运行时该路径被挂载覆盖"的组合（npmrc、pip.conf、maven settings 都中招）。
- **npm 侧"以为要补源、其实不用"**：直觉上容器内 npm 必然走境外，但**lock 文件把 resolved URL 固化进去了**，`npm ci` 严格按 lock 下载。要靠**数 lock 里的 URL 条数**才能确认，不能靠推断。
- **设计文档 §4.3 的命令写错了服务名**：文档写 `docker compose build nexus-builder`，而 compose 里的**服务名是 `builder`**（`nexus-builder` 是镜像名）。照文档抄会直接报 `no such service: nexus-builder` —— 这类"文档里的命令没跑过就写进去"的错误，只有真去核对才能发现。
- **设计文档 §5.2 的意图已不成立**：文档称"builder node:20 与 Windows 侧同一大版本，避免行为漂移"，而实测 Windows 侧是 **Node 24**。原意图落空，实际是靠依赖的 engines 兼容范围兜住的 —— **结论对，但理由必须改**，否则后人按"版本要对齐"去排查会白费功夫。
- **仓库里有两个把文件路径当目录建出来的空目录**（`docker/nginx/nginx.conf/`、`dist/backend/app.jar/`，均 0 条目），git 不跟踪空目录所以不会被发现。
- **Node 20 已于 2026-04-30 结束维护期**（官方发布计划），演示项目不阻塞，但属 watch item。

## 下次怎么改进

- **每逢"往镜像里注入配置"，先查该路径是否被挂载覆盖**：`--mount=type=cache` / `-v` / `tmpfs` 挂到某路径时，镜像层内容即被遮蔽。这是个**静默失败**（无报错、回落默认值），排查成本极高，必须在写 Dockerfile 时就规避。
- **"要不要补国内源"必须用数据回答，不能凭直觉**：本次靠 `grep -c '"resolved": "https://registry.npmmirror.com'` 一条命令定了 npm 侧的案。**凡涉及"某工具会不会走境外"的判断，都该先找一条可数的证据。**
- **文档里写的命令必须先核对其中的标识符**：服务名 vs 镜像名（`builder` vs `nexus-builder`）是高频错误点，写文档时应对照 compose 文件逐字确认。建议后续把"设计文档中的命令需实跑验证过才写入"作为纪律。
- **清理项应固化为交接清单**：误建空目录、0 字节的 `builder/CLAUDE.md` 这类残留，git 不会报错也不会跟踪，只能靠主动 `find` 扫描。建议每次阶段收尾时扫一遍"空目录 / 空文件"。
- **验证配置是否真生效，要指定可观测的判据**：本次给出的是"看构建日志里是 `Downloading from aliyun-central:` 还是 `downloading from central:`"——比"构建成功"这种模糊判据可靠得多。**配了源不等于生效，必须从日志里看到源的名字。**
