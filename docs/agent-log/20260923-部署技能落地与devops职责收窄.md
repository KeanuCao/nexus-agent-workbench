## 遇到的坑

1. ★ **新增边界会与旧原则打架，必须反查全文。** 「部署期间不写文档」写进新节之后，与工作原则里
   「完成后更新进度标记」形成**同文件内的直接矛盾** —— 只读一条会照旧原则去写文档。
   处置：裁定「文档更新归主会话」，把那行改成指针 + 交叉引用。★ 5 条冲突里有 **3 条**都是这类
   （新规则带出来的旧句），说明"改边界"这个动作**自带**一批待清理的矛盾。
2. **机制描述不变、但路径变了，读者会误解责任归属。** `db-patch-migrate` 的机制（checksum 幂等/篡改终止）
   一个字没变，但日常部署已改为 skill 第 4 步的**只读对账**（相等即跳过迁移）⇒ 只读 charter 的人会以为
   日常补丁仍由本角色手工执行。处置：加一行指针，原命令保留（它是**手工补跑**入口）。
3. ★ **文档内部的口径矛盾也要专门扫。** `check-env.sh` 的职责在三处写法不一致（第 68 行含"模型就绪"、
   第 132 行注释含"容器健康"，而陷阱 10 明确要求运行期判据归 `check-health.sh`）——
   不是"文档 vs 现实"，而是**文档 vs 文档**，同样会把执行者引到反方向。处置：按陷阱 10 拉齐三处。
4. **"被指过去却找不到调用方式"。** 上面两处收口后，charter 两次点名 `scripts/check-health.sh`，
   但「常用命令」列表里根本没有它 ⇒ 读者知道该用、不知道怎么敲。执行者**只上报不自加**（正确的边界），
   由主会话批准后补一行。
5. ★ **仓库自己推荐的 `.gitignore` 写法是错的（主会话在提交前发现）。** 原注释推荐
   「`.claude/skills/` 忽略 + `!.claude/skills/<技能名>/` 放行」，但**带尾斜杠 = 忽略目录本身**，
   git 不会下探进该目录，`!` 放行**永远不生效**（git 明确不允许"父目录被排除后再包含其子文件"）。
   处置：改成 `.claude/skills/*`（忽略目录**内容**）+ `!` 放行，并做**对照实测**：
   旧写法下 `git check-ignore -v` 仍命中该文件、新写法下不命中 ⇒ 结论写进 `.gitignore` 注释。
   附带：`__pycache__/`、`*.pyc` 也补进忽略（skill 里的 Python 脚本会留 pyc）。
6. **归因纪律的又一例**：执行者主动标注「工作区里 `.gitignore` 也被改了，**那不是我改的**，
   请确认是你或另一个 agent 的手笔」—— 多 agent 共用同一工作区时，看见别人的改动**不要认领**、
   也不要不吭声。

## 下次怎么改进

1. **改边界/职责类文档时，加一步"反查"**：新增一节后，用关键词（文档 / 提交 / 进度 / 执行 / 入口）回扫全文，
   逐条判定"这句还成立吗"，把冲突列成表交由裁定 —— 本次 5 条里 3 条都是这么捞出来的。
2. **凡是把读者"指向"某个脚本或文档，必须同时给调用方式**（一行命令或一句"怎么跑"），
   否则等于把人指到空房间里。
3. **忽略规则、路径规则这类"凭印象的写法"一律实测**：`git check-ignore -v` + **改前/改后对照实验**，
   比读文档/凭记忆可靠（本次若不做对照，就会把"永远不生效的放行"当成功提交上去）。
