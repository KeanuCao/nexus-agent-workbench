## 遇到的坑

1. **设计的 §3.8 与"§3.N↔§7.N 一比一"打架**（子代理主动上报）。
   现象：设计写"知识库业务码（进 §7.4）"，而 §3.1~§3.9 若按顺序映射到契约 §7，错误码应落在 §7.8。
   原因：那句交叉引用是从阶段2 的"§6.4 错误码"顺手抄来的**笔误**（阶段2 的 §3.4 恰好是错误码，阶段3 不是）。
   当时的处理：子代理选"让那句话成真"——把 §7.4 排成错误码增量，并给了另一条的改法。
   复核后的处置：改用**一比一**（阶段2 的既有惯例 `§6.N ↔ §3.N`，§7 开头把这条约定写死），
   一次性脚本把 §7.4~§7.8 整体位移，同步 6 个文件里的 20 处引用。判据：`grep '^### 7\.'` 得到 7.1~7.9 连续、
   且每处 `§7.x` 引用的语义都对得上。
2. **`ollama show` 看不出 `nomic-embed-text` 是 v1.0 还是 v1.5**，而检索前缀（`search_query:` / `search_document:`）
   的建议是按 v1.5 口径给的。处理：**不预判**——前缀做成可配且默认开启，"开还是关、差多少"变成
   TC-03 的 A/B 用例，用实测数字说话（写进设计的"待实测"栏而不是结论栏）。
3. **把"自己推导出的做法"记成了"用户原话"**（主会话复核时发现）。
   现象：子代理在 `.claude/agent-memory/backend-engineer/` 新增的条目里写着"2026-09-22 用户提出（原话：…）"。
   核实：`.claude/settings*.json` 无相关权限规则、`git log --all` 无相关提交、CC 文档与既有 agent-memory 均无提及。
   原因：该做法本身是从仓库既有的 `.deps-src/`、`.result/` 两条 `.gitignore` 注释**推导**出来的
   （"放工作目录内 → 普通 Read/Grep 即可读，零审批"），推导合理，但被写成了既成事实。
   处理：改写为"本 agent 引入（来源待用户确认）"，并把教训写进该条目自身。
4. **改写脚本把 6 个文件的行尾从 LF 翻成 CRLF**（主会话引入，提交前发现并重做）。
   现象：提交统计出现 `3627 insertions / 2252 deletions`，而真实改动只有几百行 —— 多出来的部分是**整份文件的行尾差异**
   （`git ls-files --eol` 显示这 6 个文件变成 `i/crlf w/crlf`，未被我碰过的文件仍是 `i/lf w/lf`）。
   原因：改号脚本用 `path.write_text(text, encoding="utf-8")` 写回 —— **Windows 上 Python 文本模式会把 `\n` 翻译成
   `os.linesep`（`\r\n`）**，而本仓库没有 `.gitattributes`、`core.autocrlf=false`，行尾是**按字节入库**的。
   处理：二进制方式还原（`read_bytes().replace(b"\r\n", b"\n")`）、`git reset HEAD~2` 后重做两个本地提交
   （未 push，历史不留痕），并给脚本补上 `newline=""`。
   判据：`git ls-files --eol <文件>` 必须是 `i/lf w/lf`；`git show --stat` 的增删行数应与"真实改动"同量级。

## 下次怎么改进

1. **跨文档的编号引用按"1:1 惯例"先定结构再写内容**。新增章节时先决定"契约 §X.N ↔ 设计 §Y.N"，
   再填内容 —— 编号是结构，结构错了要全域改（本段 6 个文件 20 处引用）。
   引用处尽量写成"§7.4（= 设计 §3.4）"这种可自证的形式，比只写一个数字抗漂移。
2. **新增依赖时"镜像源上有坐标" ≠ "Maven 能解析"**：本段用 HTTP 200 核了 `tika-core:3.2.3` 与
   `tika-parser-pdf-module:3.2.3` 的 pom/jar（及其传递依赖树），但完整解析要等 builder 首次 `build-backend`
   —— 回退链（`tika-parsers-standard-package` → 2.9.2）已写在父 POM 注释里。
3. **写"用户说过"之前先问：这句话在哪个文件/哪次交互里能指认？** 指认不出就写成"本 agent 引入"。
   这是本仓库的归因纪律，代价只有几个字，收益是后续 agent 不会把推测当既成事实。
4. **凡是用脚本批量改写文本，一律 `newline=""`（或干脆走二进制）**。本仓库无 `.gitattributes`、
   `core.autocrlf=false` ⇒ 行尾按字节入库，Windows 上 Python 文本模式的一次默认翻译就能把整份文件变成 CRLF 差异。
   改完的判据不是"看着对"，而是两条命令：`git ls-files --eol <文件>`（要 `i/lf w/lf`）、
   `git show --stat`（增删行数应与真实改动同量级 —— 数量级不对就是行尾或编码被翻了）。
