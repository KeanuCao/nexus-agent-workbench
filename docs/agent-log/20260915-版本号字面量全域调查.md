## 做了什么

为回答「backend 版本号为什么每次要改多个地方」，两路并行扫了「版本号到底出现在哪些地方」：

1. **backend 内部**：`backend/pom.xml:39` 是唯一真源，但 5 个子模块的 `<parent><version>` 各写了一遍字面量（`nexus-common:18` / `nexus-infrastructure:39` / `nexus-module-system:27` / `nexus-module-ai:17` / `nexus-start:19`）→ 一次发版要动 6 个文件；并顺带查清运行时链路：`application.yml:97` 的 `@project.version@`（靠 `spring-boot-starter-parent` 默认的 `@` 分隔符过滤）→ `NexusHealthProperties` → `GET /api/health` 的 `data.version`。
2. **backend 之外**：`docker-compose/`、三个 Dockerfile、`scripts/` 全部**不含**后端版本号（脚本只做 semver 形状校验 + 拒绝 `@..@` 字面量）；版本号只散在**文档与示例**里，共 20 处（`docs/api/README.md` 8、`docs/api/openapi.yaml` 5、三个 README 的 jar 文件名 3、design 00 样例 1 等）。

## 遇到的坑

- **差点把「现状不一致」当成「本次现象的原因」**：查到「父 POM 0.2.1 / 子模块 0.2.0」后，第一版结论直接说这就是「换包测试没生效」的原因。实际直接原因是**容器拉的是远端 main**（`docker-compose/.env:30`），而 main 上父子都是 0.2.0、自洽；漂移只是尚未引爆的隐患。→ 现象归因必须同时看「本地分支」与「构建源」两侧。
- **拿到了一个推论当结论**：「Maven 会静默回落到本地仓库里的旧父 POM」当时只是读源码/文档得出的**结构推论**，并未运行 Maven 验证。项目对「实测 / 推断」分得很严，该结论后来被排成改造前的第一道实测关卡。

## 下次怎么改进

1. 涉及到「构建/运行期行为」的调查结论，在交付时就**标注来源等级**（官方文档 / 源码 / 实测 / 推断），主会话不必回头逐条甄别。
2. 归因「某改动没生效」时，**先问这个提交进构建源了吗**（本项目构建源是远端 main，push 与合并由用户手工做），再谈代码层原因。
