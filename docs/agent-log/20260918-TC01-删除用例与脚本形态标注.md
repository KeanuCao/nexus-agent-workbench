## 遇到的坑

1. **⚠️ 主会话的复核理由里有一处说错了：它说"豁免生效已被 1.3-4 / 1.4-1 覆盖"—— 而 1.3-4 这一轮正在被删。**
   等于**拿一个自己正在删除的东西当依据**。若不核就照写，附录会留下一个指向空号的"覆盖来源"。
   → 处理：改成只写 **1.4-1**，并在回报里明确订正主会话的转述。
2. **原 1.3-3 的判据①照字面执行会得出「相反」结论。**
   判据①写的是「SQL **不含** `tenant_id` 条件」，可那条 SQL 的**列清单里就有 `tenant_id`**（`UserMapper.java:40`：`SELECT user_id, tenant_id, username, ...`）—— grep 一下"含不含 tenant_id"，命中的是**列清单**，不是 WHERE 条件。
   这是"执行者必须自行翻译"的又一实例，也是支持删除的**硬证据**（主会话的转述里没有这条）。
3. **原 1.3-4 里那个单测指针本来就不准，不是"删了才丢"。**
   主会话说它"一字不差地也在附录里、删掉不丢信息"—— 复核后**不完全属实**：`TenantContextTest` 这个名字**只**出现在被删那行，附录里没有。更要紧的是，核了 `TenantContextTest.java` 后发现它覆盖的是 `TenantContext`（ThreadLocal 持有者的 set / clear / 豁免压弹 / 异常配平），**全测试树里没有一个用例碰 `TenantLineHandlerImpl.getTenantId()` 的抛异常分支**。

## 下次怎么改进

1. **删除任何一条用例 / 文档时，先列出「它引用了谁」和「谁引用了它」两张表，再动手。**
   本次的坑 1 就是漏了第二张表 —— **被删对象常常正被别处当作依据**。判据：删完之后 grep 一次它的编号，命中的每一处都要有处置（改写 / 标注已移除 / 确认是另一套编号）。
2. **判据里出现「不含 X」「没有 X」这类否定式断言时，先 grep 一遍 X 会不会在同一处出现。**
   否定式断言最容易撞词 —— 列清单、注释、别名字段都能让它"看着命中"却含义相反。**正面断言不会有这个问题，能用正面就别用否定。**
3. **交接里说「内容完全重复、可安全删」时，要逐字核，不要采信摘要。**
   "大意相同"和"一字不差"是两回事；**指针类内容（类名、编号、文件路径）最容易在浓缩成摘要时丢掉** —— 而丢一个指针，就等于让读者少一条追查路径。
4. **"卡住 → 想删"这个动作本身值得走一遍「它在守什么」的复核，而不是直接照删。** 本次两条都删得对，但结论是复核出来的（三条理由各自成立、且各补了更强的证据），不是顺着用户的意见点头。
