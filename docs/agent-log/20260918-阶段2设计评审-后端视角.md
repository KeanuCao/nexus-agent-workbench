## 遇到的坑

1. **`SseEmitter` 的类路径够不着 —— 设计 §4.1 声明"无需新增依赖"，照做必编译失败。**
   `SseEmitter` 属 `spring-webmvc` 制品，而 `nexus-module-ai` 只依赖 `nexus-common` + `nexus-infrastructure`，infrastructure 只声明了 `spring-web`（其注释还写明刻意不带 MVC 链）；`spring-webmvc` 只在**下游** `nexus-start` 的 `starter-web` 里。
   讽刺点：设计**自己**在 §1 用"module-ai 看不到 nexus-start"这条规则论证了 D7（够不着 `OllamaProbe`）—— 规则用对了，却没套用到 `SseEmitter` 上。旁证：全仓 grep `org.springframework.web.servlet` 在三个非 start 模块下零命中，"模块里不出现 MVC 类型"是现状而非巧合。
2. **同一份设计里，"降级链"有四种说法。**
   §6.4 写"密钥缺失 → 选 DeepSeek → `20100`"（= 本轮不做降级），而 D7 / §3.2 的 `servedBy=fallback` / §4.2 的 alt 分支 / §7 的降级单测 / §10.1 的"最先落地"都断言本轮**有**降级链；§6.2 的配置块里**没有任何 fallback 键**。
   两种走法都会静默出错：按 §6.4 → §7 的单测落不了地；按 D7 → 无密钥时选 DeepSeek 会**悄悄改用 Qwen**，于是验收 2.2-1 以"看着跑通了其实是本地模型"的方式**假通过**。
3. **"开流前失败 → `Result` + 503"物理上不可能（§3.3 表 vs §4.2 时序图）。**
   `SseEmitter` 是在 controller **返回时**才交给容器的，worker 必然在它之后才跑；等 worker 发现"上游不可达/降级耗尽"，响应已经是 200 + `text/event-stream`，发不出 `Result`+503。
   **这条与前端视角独立撞车** —— 前端同事从"前端可见行为不同"的角度报了同一条矛盾（`20100` 的载体）。两端各自独立发现同一处，是很强的信号。
4. **`503 + 20100` 在既有异常体系里没有出口。** `BusinessException`→200、`SystemException`→500、兜底→500；照 §4.1 清单实现会得到 200 或 500，**拿不到 503**。线程池满抛的 `TaskRejectedException` 更是直接落兜底 → 50000。503 的既有先例是 `HealthController` 直接返回 `ResponseEntity.status(...)`。
5. **参数校验选型未定，且 400 与已发布契约冲突。** 全仓无 Bean Validation（`@NotBlank` 编译不过；即便补注解，Boot 3 的 starter-web 不带 hibernate-validator 会**静默失效** → 40001 出口成死代码）。而 `docs/api/README.md` §1.2 明确把"参数不合法"归入"业务失败 → HTTP **200**"，openapi.yaml 头部**连 400 都没列举**；§6.7 又规定"§1~§5 编号一律不动" → 矛盾会被原样合进契约。
6. **`D10` 把未验证的定时推断写成了肯定句。** 前提**核实成立**（`TenantContext` 是纯 `ThreadLocal`、过滤器 `finally` 里 clear、跨线程绝不可见 → 显式透传这个动作对），但"**立刻**清掉"没标待实测：按 Servlet 异步语义，异步启动后过滤器链是被挂起的，`clear()` 更可能发生在异步完成之后、由容器线程执行 —— 那么被污染的是**容器线程池**而非工作线程，阶段3 撞上时排查方向不同。
   处理：拆成「工作线程必无上下文（已核实）→ 必做」+「`clear()` 的确切时机待实测」。
7. **`D1` 方向对，但退路不完整。** `RestClient` + JDK `HttpURLConnection` 对 chunked 确实能增量交付、用 curl `-N` 目视判据也对；但 `exchange()` 返回后响应可能**已被关闭**（`RestTemplate.doExecute` 家族惯常在返回时 close，`SimpleClientHttpResponse.close()` 还可能 drain 流）—— 那不是"增量与否"，而是"**流还在不在**"，而文档的退路只覆盖了前者。建议直接把实现形状定成基于 extractor 的 `execute(...)`，并把 `AiModelService` 的签名定成**回调式**（设计原文留了"回调 **或** 返回 Stream"二选一，而这是全设计最承重的接口，不该留二选一）。

## 下次怎么改进

1. **设计里新增一个类之前，先把它的 FQN 写出来、确认落在哪个模块的编译类路径上。**
   本次第 1 条只差这一步：`SseEmitter` 的类型归属（`spring-webmvc`）和模块的依赖（只有 `spring-web`）一比对就出来了。判据：**凡是"我在 X 模块里 new 一个框架类型"，先问"这个类型的制品在 X 的 classpath 上吗"**，不要用"spring-web 是传递依赖"这种整体印象代替逐制品核对。
2. **同一份设计里，同一个概念只允许一种说法。** 本次"降级链"在四处出现、两两矛盾，而这四处的作者都是同一份文档 —— 这类矛盾不是理解分歧，是**写到后面忘了前面**。
   可执行做法：设计定稿前，把核心名词（降级链、`servedBy`、`meta`、`20100`）各 grep 一遍，逐处确认口径一致。
3. **凡是"某状态在某个时刻如何"的断言，先问"那个时刻由谁触发"。**
   第 3、6 两条同源：都是把"时序"当成了可以随意描述的属性，而 `SseEmitter` 的返回时刻、filter 的 `finally` 执行时刻**都由容器决定**。判据：**涉及异步/回调的时序断言，默认要标待实测，除非有文档或实测支撑**。
4. **声明"无需新增依赖"之前，先把该模块的 pom 打开看它现在有什么。** 本次 §4.1 同时漏了 3 个依赖：`spring-webmvc`（编译期，SseEmitter）、`spring-boot-starter-test`（模块里压根没有测试依赖，§7 的单测编不过）、validation（编译期 + 运行期实现）。
   判据：**"无需新增依赖"这句话，只有在"本轮新增的每个 import 都能在现有依赖里找到"时才能说** —— 逐 import 核，不要按模块印象核。
5. **派评审时明确要求"反向核对"：不仅要报问题，还要报"设计说的事实我核了、属实"。**
   本次后端同事核了 11 项"属实"（含自己复跑 `git check-ignore` 验证文档的实测记录），这才让主会话能区分"哪些要改"和"哪些别再动"。只报问题的评审，会让人误以为整份文档都需要重写。
