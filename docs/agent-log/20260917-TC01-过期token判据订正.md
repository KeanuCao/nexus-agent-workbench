- **触发**：用户手工走 TC-01 到 1.2-3 时问「这个 `nexus.jwt.expire-minutes` 怎么改」

## 做了什么

1. **复核主会话给的 4 条线索，逐条回源码确认**（行号已核）：`expire-minutes` 全仓库只命中 TC-01.md 那一行；实现绑定的是 `nexus.jwt.expire-seconds`（`application.yml:113` / `JwtProperties:35`）；`TokenStore.save` 有 `ttlSeconds <= 0` 守卫；`JwtAuthenticationFilter` 的「② 解析（含有效期）→ ③ Redis 白名单」顺序；`docker-compose.yml` 的 `nexus-backend.environment` 确实没有 `NEXUS_JWT_*`。
2. **订正 TC-01.md**（4 处）：① `:36` 换成夹具路线（原格键名不存在 + 不可执行，两个错叠加）；② 新增「TC-01-1.2-3 备注」行，写清为什么不走「改配置」路线、等价性依据、以及「拿到 40101 该怎么分诊」；③ `1.4-1` 的 `expiresIn=7200` 加注来源；④ `1.2-5` 的步骤由速记展开为可复制粘贴的完整命令（**语义未改**）。
3. **新建夹具 `qa/scripts/tc01-expired-token.sh`**：python3 标准库（hmac/hashlib/base64/json/uuid/time）本地签一个「签名正确、`exp` 已过 60 秒、`jti` 从未进过 Redis」的 token。**只做本地计算 —— 零副作用**，属 Test Harmlessness §1 的「只读观察」档，无需清理步骤、无需指纹自证。已在 WSL 实跑并独立复算签名（`True`），错误分支与退出码（0/2/3）逐个验过。
4. **上报并订正一处编号冲突**：`1.2-3` 在本仓库有**两套编号**（详见「遇到的坑 3」）；TC-01 头部加了编号对照表，`docs/api/README.md` §5.3 的失效引用改成 `TC-01-1.2-5` 并补了变更记录行。
5. **未跑任何 docker / compose / curl**（用户手工验收）；TC-01 的「实测」栏一条未填 —— 本轮的结论全部是静态复核 + 夹具自身的离线自测。

## 遇到的坑

1. **一个失效判据里叠了两个错，任何一个都足以让执行者卡住。**
   `TC-01.md:36` 原文「用 `nexus.jwt.expire-minutes` 改成 `0`（或等其过期）重签一个」——
   ① 键名 `expire-minutes` 不存在（实现是 `expire-seconds`）；
   ② 即便键名改对，取值 `0` 也走不通：`TokenStore.save` 的 TTL 正数守卫会抛 `SystemException`，
   `GlobalExceptionHandler` 转成 **HTTP 500 + code=50000 +「系统繁忙，请稍后重试」**，登录拿不到 token。
   → 处理：不挑其中一条照做，按「判据要能指向一个真实存在的开关」重写成夹具路线，并在备注行把两条错都写明。
2. **「改配置」这条路的真实成本被低估了**：改 `expire-seconds` 要重建 `nexus-backend`（yml 打进 jar 由 builder 产出，宿主改不到），
   而 compose 里根本没有 `NEXUS_JWT_EXPIRE_SECONDS`（靠 Spring 松散绑定才认）—— 得先改 compose 加一行。
   生效期间**其他用例**登录拿到的 token 也会秒过期，属污染。
   → 处理：换成「本地签一个已过期的 token」。判据等价，因为过滤器的 **② 在 ③ 之前** —— 真过期的 token 也是先撞 ② 回 40102，两条路在过滤器里是同一条。
3. **两套编号撞车（本次最大的发现）**：`1.2-3` 这个编号在两个体系里指向的事不同的用例。
   - `design/01` §9 / `task.2` / `api/README` §5.3 的 `X.Y-N` = **task 原文的第 N 条验收标准**（§1.2 只有 3 条）；
   - `TC-01.md` 的 `TC-01-X.Y-N` = **第 N 条用例**（§1.2 有 6 条，因为 task 的第 1 条被拆成了 1.2-1/2/3）。
   → 撞车两处：`1.2-3`（design=登出即失效 ↔ TC=过期 token）、`1.4-3`（design=token 可访问受保护接口 ↔ TC=用户不存在）。
   → 处理：**不动任何一方的编号**（TC-01 的编号正在被用户手工验收使用，改号会破坏在跑的记录），
   改为在 TC-01 头部加对照表；`api/README` §5.3 那句改成写用例名 + `TC-01-1.2-5`。
   发现方式：本来只想核对 1.2-3，顺手 grep 了全仓库的 `1.2-3` 才看出来。
4. **Windows + WSL 的一个自伤**：从 Git Bash 调 `wsl -d <distro> -- bash /mnt/c/...` 时，
   MSYS 会把 `/mnt/c/...` 改写成 `C:/Program Files/Git/mnt/c/...` → `No such file or directory`。
   → 处理：调用前加 `MSYS_NO_PATHCONV=1`。**只影响「从 Git Bash 里调 WSL」这一条路径**，
   用户在 WSL 内直接跑（TC 的写法）不受影响 —— 但这解释了「为什么我自己跑得通、你照抄却报找不到文件」这类怪现象的来源。
5. **写夹具前先探测依赖**：主会话只说了「WSL 无 `jq`」，没说有没有 `python3`/`node`。
   实测：`/usr/bin/python3`(3.12.3)、`openssl`、`perl`、`xxd` 都在，**`node`/`nodejs`/`jq` 都不在**。
   夹具因此选 python3 标准库（而不是自拼 `openssl base64` 的 base64url —— 要手工去 padding，多一处可错的地方）。

## 下次怎么改进

1. **判据里出现配置键名 / 文件名 / 接口路径时，落笔前当场 grep 一次。**
   「全仓库只命中我这一行」就是判据已经失效的强信号 —— 本次若早 grep 一次，`:36` 那格不会活到现在。
2. **TC 编号与上游文档（design §9 / task）的编号是两套体系**：凡引用一律带 `TC-01-` 前缀或直接写用例名。
   遗留：TC-00.md 头部可能也有同样的对照问题，本轮未查（属阶段0 的历史判据，需单独复核）。
3. **需要「坏 token / 坏数据」的用例，优先「本地造一个只读观察的东西」，而不是「改 SUT 配置」**：
   判据等价（前提是**先读一遍被测组件的判定顺序**，本次靠「② 在 ③ 之前」成立），
   成本却从「改配置 + 重建容器 + 污染其他用例」降到零。这是 Test Harmlessness §1 优先级 1 的具体复现。
4. **夹具交付前必须自己离线跑通并独立复算**（本次：HMAC 独立重算 + 逐项 decode + 三个错误分支的退出码）。
   只写不跑的夹具，等于把「不可复现」从用例搬到了脚本里。
5. **「有意守卫」与「缺陷」要分开下结论**：`TokenStore` 的 `ttlSeconds <= 0` 守卫是**有意的**（TTL 非法就该炸），
   不是缺陷；但「配置错到第一次登录才以 HTTP 500 + 通用话术暴露」有一处**可改进**（见回报正文的遗留项），
   这类结论只上报、不代改代码。
