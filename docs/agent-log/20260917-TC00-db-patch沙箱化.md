## 遇到的坑

1. **派活时漏了「必须先 push」这个前提**：探针夹具在 `qa/`（未跟踪状态），而 builder 的 `/workspace/repo` 是 clone、`git-sync` 只认远端提交（且 `checkout --force` + `clean -fd`）→ **不 push，用例第一步就会以「文件找不到」失败**，而这正是最难归因的一类失败。
   → 处理：它自己识别出来，把 `commit → push → 合入 main → git-sync` 写成 0.2-0 的 ①②，并加一步存在性验证（`ls` 失败即「① 没生效，别往下走」）。
2. **用例之间存在隐含的状态依赖**：0.2-4（乱序保护）的判据依赖「已应用的最大 `file_name`」，而 `PatchCli` 只在扫描补丁前取**一次** —— 探针没落库时基准会退回真实补丁名，`209912310005` 反而不构成乱序、会被**正常应用**（`exit=0`，判据静默失效）。
   → 处理：写进步骤与预期，并给出「见到 `exit=0` 先回去补跑 0.2-3 ①」的分诊指引。
3. **它自己初稿里的一处事实错误**：以为 B 先于 A 执行会报「relation 不存在」，实际首先撞的是 `schema "tc00_probe" does not exist`（schema 也是 A 建的），只有 schema 已存在时才轮到 relation 报错。
   → 处理：自查后订正夹具注释与 TC 预期，写成「两种报错之一，都是 `exit=4`」。

## 下次怎么改进

1. **凡用例要把文件带进 builder 容器，先确认它是否「已 push 到远端」** —— 容器 clone 不认工作区里的未跟踪/未提交文件。这类前置必须写成用例的**第 ① 步 + 一步存在性验证**（照做即用），不能只写在说明文字里。
2. **共享沙箱的用例必须显式声明「我依赖前面哪一步留下的状态」**，并在预期栏给出「状态不对时看到什么现象、先回去补哪一步」。本次 0.2-4 的 ⚠️ 可直接作为模板。
3. **判据要「由被测对象自己证明」，而不是靠日志看起来对**：B 依赖 A 的产物让「按序执行」由数据库证明。同类场景（顺序、隔离、幂等）都该找这种「违背即报错」的设计 —— 比比对日志行强得多。
4. **给测试夹具加「作用域守卫」**（如 `current_database()` 断言）：把「漏注入作用域开关 → 污染真实对象」这类灾难**降级成响亮的失败**（单事务回滚、真实对象零写入、退出码 4）。本次探针带 2099 时间戳，漏一个 `-e NEXUS_PG_DB` 就会毒化真实 `t_db_patch` 的「最大文件名」基准、让此后所有真实补丁判乱序 —— 这类「延迟爆发且不像测试造成的」后果，最值得加守卫。代价是守卫里硬编码了作用域名，改名要同步改夹具。
5. **派活时给的事实也要留出「让执行者自己核」的空间**：本次任务说明里的行号、退出码、种子行数，它都回读源码核对了一遍（发现我漏说 `exit 1/4/5/9` 四个码）—— 这类「我给的 vs 你核过的」双轨，应在派活模板里固定要求。
