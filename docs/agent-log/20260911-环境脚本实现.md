- **说明**：本条记录的是一次**撞轮次上限后收尾的运行**（`maxTurns: 50`，第二次撞）。三个脚本文件均已落盘且语法通过，撞限时处于**验证阶段**而非编码阶段。

## 做了什么

- 产出三个脚本（均已 `bash -n` 通过、均已 `chmod +x`）：

| 文件 | 行数 | 职责 |
| --- | --- | --- |
| `scripts/lib/probe.sh` | 473 | 探针共享函数（6 个） |
| `scripts/check-env.sh` | 375 | 启动前置自检（8 项 + 1 凭据子项），FAIL 即中止 |
| `scripts/up.sh` | 298 | 一键拉起（§4.3 九步） |

- **主动把探针抽成独立库** —— 与并行进行的 task-decomposer 把 `probe.sh` 单列为 **0.3.5** 的决策**不谋而合**（两边独立得出同一结论，可作为该设计判断的交叉验证）。
- **`.env` 凭据陷阱的处理超出要求**：不是写句提示了事，而是做成独立检查项 **4b**，并**解析 `application.yml` 提取 `${POSTGRES_XXX:default}` 的默认值**（`yml_pg_default` 函数）与实际 `.env` 对比，从而**自动检测这个静默耦合**。
- **模型就绪只判 WARN**，且在注释里**专门警告后人别改**："理由（必须写清楚，否则后人很容易'顺手改成 FAIL'）"。
- **`up.sh` 第 4 步条件执行**，且脚本头部把三条坑逐条列出（含我们踩过的"第 2 步必须显式点名服务"）。
- **主动解释了一处关键取舍**：`up.sh` **刻意不启用 `set -e`** —— 九步中"必须中止"（构建失败、依赖不健康）与"只告警继续"（模型拉取超时）两类语义混杂，全局 `-e` 会把后者也变成中止；且 `$(...)` 内非零返回（如 `grep` 无匹配）会被误判为致命错误。
- **把防错写进文件本身**：`check-env.sh` 头部标注"判据来源（唯一事实源，**别从 `docs/drafts/环境检查脚本.md` 抄** —— 该草稿有 8 处判据已核实有误）"，并附"明确不做"清单。**下一个人或 agent 拿到脚本不会再把草稿的错误引回来。**

## 遇到的坑

- **`maxTurns: 50` 第二次撞限（本项目已累计两次）**：上一次是诊断任务、这次是实现任务。两次都**卡在收尾**，且**停止是静默的** —— 只返回一句进行中的话（"The mock files failed to write..."），若不主动查磁盘会误以为任务正常完成。**实际上三个脚本都已完整落盘**，撞限点远晚于 partial 消息给人的印象。
- **把重型验证放在了最后**：撞限时它在用 mock server 验证 timestamp 分支，而 `/tmp` 对 Windows 侧 Python 不可见导致 mock 文件写不进去。**这类"环境本身不受控"的验证方式，投入产出比极低** —— 换成静态说明（贴出解析代码解释各分支处理）即可，却消耗了本可用于汇报的轮次。
- **`.env` 凭据耦合是本次最有价值的发现**（由 backend-engineer 首先发现、devops 落地为检查项）：compose 里 postgres 用 `${PG_USER}/${PG_PASSWORD}/${PG_DB}`，而后端容器的 `environment:` **只有 `SERVER_PORT`**，后端能连上 **纯粹因为 `application.yml` 默认值恰好与 `.env` 相同**。→ 用户照"改 `.env`"的提示改了密码，会**亲手造成后端连不上**，且不知道原因。
- **交付与验证的次序问题**：脚本已完整产出，但**未经验证**（agent 被禁止执行 docker）。所以交付物处于"看起来完成、实际未验证"的状态，需要用户实机确认。

## 下次怎么改进

- **`maxTurns` 必须提高（本次第二次撞限，建议立即处理）**：`devops-engineer` 50 → 80~100。两次事故都证明：撞限**不报错、静默截断**，主会话必须主动 `find` 核对产物才能识破；而一次撞限的续跑成本（重读上下文 + 重新定位缺口）**远高于**放宽上限的理论成本。**这是本项目当前最高频的失败模式。**
- **把"汇报"提到"重型验证"之前**：agent 应先在产出完整时输出汇报，再按剩余轮次决定是否深挖验证。**否则容易在验证环节撞限，导致汇报缺失** —— 而汇报才是主会话与用户最需要的。
- **验证手段要与环境控制力匹配**：环境不受控（如跨 Windows/WSL 的文件可见性、无法启 mock 服务）时，**主动降级为静态验证**（说明代码如何处理各分支），不要硬搭临时设施。
- **"配置耦合"应作为一类检查固化下来**：凡是多容器共享的配置，都要问一句"这个值在每处是怎么拿到的"。"默认值恰好相同"是一种**静默脆弱耦合** —— 两边各写各的，改任一侧就断，且断在运行期。
- **把"防止后人重犯"写进产物本身**（本次 `check-env.sh` 头部的"别从草稿抄"+ "明确不做"清单是范例）：对于已被证伪的做法，**在离现场最近的地方留警示**，比写在 agent-log 里有效得多 —— 因为后续的 agent 未必会读到留档。
