# 版本号单点化方案设计（`${revision}` + flatten-maven-plugin）

- **Agent**：Plan ｜ **耗时**：约 8 分钟 ｜ **task-id**：a26508d1c6fd28b2d

## 做了什么

产出可直接执行的改造方案：

1. **具体改法**：父 POM `<version>${revision}</version>` + `<properties><revision>0.2.1</revision></properties>` + flatten 插件块（`flattenMode=resolveCiFriendliesOnly`、`updatePomFile=true`、flatten 绑 `process-resources`、clean 绑 `clean`）；5 个子模块 `<parent><version>` 改 `${revision}`；`.gitignore` 加 `.flattened-pom.xml`。
2. **逐条回答 6 个风险点**：不装 flatten 会让 install/deploy 出去的 pom 不可被消费者解析；`.flattened-pom.xml` 落 `${project.basedir}`、**不进 `target/`**，与「恰好一个 jar」的约定零交集；`${revision}` 让子模块 parent GAV 与 `../pom.xml` **必然字符串相等**（Maven 解析父 POM 时逐字比较、不做插值），从结构上消除漂移；`@project.version@` 过滤出的仍是具体版本号；与父 POM「刻意不绑定任何插件」的注释冲突、须改写为「默认不绑定 + 一条准入判据」；`mvn -Drevision=x.y.z` 可用且必须保留 POM 里的默认值（容器构建跑的是裸 `mvn clean install`）。
3. **实测（非推断）**：阿里云 public 源上 `flatten-maven-plugin` 最高 `<release>` = 1.8.0、可下载（129.7KB），`prerequisites` 要求 Maven 3.6.3（builder 是 3.9）→ 新增插件不构成离线风险。
4. **备选方案对比**：`versions:set`（只消灭手抄、不消灭结构）、git tag/`git describe` 推导（会让版本号变成 `0.2.1-4-gabc1234` 这种带后缀的形式，**违反项目里 `^\d+\.\d+\.\d+$` 的既有契约**，且改造构建链路风险高）。

## 遇到的坑

- **子代理把「外推」写进了结论**：它根据我给的背景（`docker compose exec builder` 在 0.1-7 里失败）推测根因是缺 `--profile build`，我一度采信并准备写进测试记录。**该推测是错的** —— 主会话实测：builder 运行中时，`docker compose exec builder` 带不带 profile 都返回 `EXEC-OK / exit=0`。它只验证了 `config --services` 的输出（不带 profile 时服务列表里没有 builder），把「服务模型不含它」外推成了「exec 会失败」。
- 真正的原因至今未定 —— 用户当时在命令层面就失败了，**没有拿到报错原文**，按项目纪律不写根因。

## 下次怎么改进

1. `docker compose` 的 `config --services`（模型层）与 `exec`（运行期）是**两条不同的代码路径**，前者的输出不能用来推断后者的行为 —— 这类「同一条命令的不同子命令」的外推要格外小心，一句话就能验的事不要靠推。
2. 拿到「某命令失败」的二手描述时，**先要错误原文**再谈根因；给子代理的输入里也要把这点写清楚，否则它会基于不完整信息补一个看似合理的因果链。
