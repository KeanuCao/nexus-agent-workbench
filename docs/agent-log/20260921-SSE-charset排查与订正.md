# SSE 响应头的 `charset`：一次「实测 vs 文档」的排查与订正

- **执行**：主会话（查规范、拍板判断、收口）＋ 子代理 `backend-engineer`（4 处文档措辞）与 `qa-engineer`（用例 3 处措辞）
- **性质**：主会话留档（**非** hook 自动归档 —— 两个子代理单次耗时均 < 2 分钟，未触发归档阈值；由主会话合并记录）
- **触发**：`TC-02-2.1-1` 实测后读响应头，发现是**裸** `Content-Type: text/event-stream`，而用例判据 ① 写的是 `text/event-stream;charset=UTF-8`
- **结论**：**后端刻意不加 charset**（保留裸值）；订正的是**措辞**（6 处），**代码零改动**

## 做了什么

1. **先判断「该不该加」，再决定「谁写错了」** —— 顺序很关键。查规范原文：SSE 的 IANA 注册里 `charset` 是**可选**参数，且原文写着「**serves no purpose; it is only allowed for compatibility with legacy servers**」；WHATWG HTML 标准：「Event streams are always decoded as UTF-8. There is no way to specify another character encoding.」⇒ 加它**不改变任何行为**；而本契约 §6.1 声明的就是裸值，实现一致 ⇒ **不该加**。
2. **于是"错"的是理由，不是结论** —— 原措辞是「判 `application/json` 必须用 `includes` 而非全等，**因为 Spring 会给 `text/event-stream` 带上 `;charset=UTF-8`**」。实测：SSE 侧**不带**、失败形态的 JSON 侧**带**（`application/json;charset=UTF-8`）⇒ 两边形态**本就不一致**，「别用全等」这个**结论是对的**，只是理由指错了对象。
3. **补上机制（能讲"为什么"的那种）** —— 失败侧是**手写响应**（`JwtAuthenticationFilter.writeUnauthorized()` 里 `setContentType(APPLICATION_JSON_VALUE)` + `setCharacterEncoding("UTF-8")`），成功侧是 `SseEmitter` + `produces = text/event-stream`（**没人设编码**）。**两类不同的写入者 ⇒ 形态不一致是必然**，不是偶发。
4. **订正范围按"一句错理由复制到几处"来定：共 6 处** —— `docs/api/README.md` §6.3、`docs/design/02-统一AI网关.md` §5.1-2、`docs/api/openapi.yaml`（**两处**，其中一处是**直接断言成功响应头带 charset**，与实测正面冲突，最重）、`frontend/src/api/chat.ts` 注释、`ChatController.java` javadoc。全部**只换理由半句**，`includes('application/json')` 等结论一字未动。
5. **用例侧同步**：`TC-02.md` 判据 ① 改为裸值；`2.1-1` 的「实测」栏①同步；§7 第 4 行从"偏差"改写为「已拍板『不加』+ 已订正」。
6. **留痕纪律**：`docs/agent-log/20260918-阶段2设计评审-前端视角.md` 里也有同款说法 —— **原样保留**（日期化留档，改它等于篡改；新记录里写明"按不改历史留档保留"，免得以后有人当新发现再报一遍）。

## 遇到的坑

1. **★ 「理由错、行为对」是最难发现的一类错** —— 代码行为正确（用 `includes`）会让人以为整句话都对，错的理由就顺着注释、文档、契约一路复制了 **6 处**。行为正确**不构成**理由正确的证据。
2. **判据会照抄文档的说法** —— 用例判据 ① 的 `;charset=UTF-8` 不是实测得来的，是从文档里抄的。**判据的措辞如果来自文档而不是实测，它测的就是"文档自洽"，不是"系统行为"。**
3. **"非空 ≠ 有效"的同族陷阱（同日另一件事）** —— `.env.local` 里两行同名 `DEEPSEEK_API_KEY`，compose 的 `env_file` 是**后行覆盖前行** ⇒ 真密钥被一个 14 字符占位值遮蔽，而**启动日志照样打 `apiKey已配置=true`**（它只判非空），直到第一次云端请求才以 `401 ⇒ 20100` 现形。同一个道理：**日志说"已配置"不等于"配置有效"。**
4. **测试工具自己也会静默失效（同日第三件事）** —— 过滤器 `tc02-stamp-lines.py` 的 `feed_line()` 漏了 `return`，逐行回显整片变成 `None`（响应头与每一帧都读不到），而**汇总统计全对、`--self-test` 全绿**。⇒ 自检只覆盖了"统计"，没覆盖"人看的那条输出路径"。

## 下次怎么改进

1. **文档里的"因为…"要按事实核一遍再抄** —— 尤其是被多处引用的那句。判据/注释/契约里凡是出现"因为/由于/Spring 会…"的因果句，都是**待验证的断言**，不是背景。
2. **发现"结论对、理由错"时，只换理由、不动结论** —— 并在同一次把**所有复制处**一次改完（本次 6 处）；漏一处，下次还会有人从那处抄回去。
3. **写判据时，判据的措辞必须能追到"实测值"或"规范条文"**，追不到的就别写进判据（本次判据 ① 就是照抄的反例）。
4. **给测试工具的自检加一条"输出路径"检查**（本次已补两条：`feed_line` 必须把行原样交回）—— 只查统计的自检，挡不住"人看到的东西是坏的"。
5. **顺序纪律**：先说清"该不该"（规范 + 契约 + 依赖方），再说"怎么改"。反过来做，就会变成"谁改谁对"的扯皮 —— 而这类问题的答案通常不在代码里，在规范里。
