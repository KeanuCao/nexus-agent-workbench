## 做了什么

1. **按主会话给的 10 组验证价值排序逐条落点**，其中最难的几条做了特殊处理：
   - **中文乱码**做成**Console 一行命令判据**：`document.querySelector('.chat-list').innerText.includes(String.fromCharCode(0xFFFD))` 必须为 `false` —— **用编号而不是那个字形**，避免粘贴时字符本身变形导致判据失效。
   - **EOF 第三出口**用 `docker compose restart nexus-backend`，作用域/恢复/自证写进步骤。
   - **池满 503** 给了两步手工造法（压 `CORE/MAX` 到 1，2 条并发即可复现），标"默认不跑"，用例内自带还原 + 还原自证。
   - **两种 20100 载体**分开成两条，其中"无密钥选云端**不得出现 qwen 回答**"是 D7 的防假通过判据。
2. **新增 3 个测试资产**：`tc02-chat-stream.sh`（登录 → 发流 → **响应头与每一帧带到达时刻**原样打印 → 抓 `[chat]` 日志 → 登出 + Redis 键清单指纹）、`tc02-pool-full.sh`、`lib/tc02-stamp-lines.py`（逐行打时刻 + 机械统计：事件计数 / data 行首末时刻 / 严格 UTF-8 解码 / U+FFFD 次数 / delta 正文拼接）。**三者都不打 PASS/FAIL，判据全在 TC-02 里**；复用 `lib/tc-common.sh` 且**未改动它**（前端端口解析只有 6 行，写在 tc02 脚本内，不碰 TC-01 的共用库）。

## 遇到的坑

1. **★★ 实测撞出一个真缺陷：缺 `Content-Type` 时后端返回 `500 + 50000「系统繁忙」`，而契约承诺的是 415。**
   `HttpMediaTypeNotSupportedException` 没有专门出口，落进 `@ExceptionHandler(Exception.class)` 兜底。后果是：**调用方的请求格式问题被报成服务端故障**，而契约（`README` §6.1 / 设计 §5.1-2）恰恰把 415 写成前端诊断"是不是 Content-Type 没带"的依据 —— 那条诊断链路整个失效。
   → 处理：**未改契约、未改代码**（那是 backend 的活），**上报**；主会话独立复现确认后当日修复（`0f4c1e0`）。
   **这条是"跑一遍判据本身"撞出来的** —— 静态复核、单测、CI 全都照不到它。
2. **主会话给的 401 造法是错的，走不到被验的那个请求。**
   原造法"对话页把 token 改坏后发送"：`/chat` 是受保护路由，刷新后路由守卫先调 `GET /api/auth/me`（axios 链路）就把人弹回登录页了 —— 那是**已被 TC-01-1.5-3 覆盖的另一形态**；而只改 localStorage 不刷新，内存里的 token 仍然有效。
   → 处理：改成"**新开标签页点退出登录**（服务端作废该 jti）→ 回原标签页发消息"，仍是零配置改动的 UI 造法。
3. **一处虚惊，主动排除并写进文档**（免得别人再查一遍）：`produces=text/event-stream` 会不会让 `10200`/`40001`/`503` 这些"开流前"的 `Result` 出口写不出去（没有能把 `Result` 写成 `text/event-stream` 的转换器）？
   **源码级核实为否**：`DispatcherServlet.processHandlerException` 第一句就是 `request.removeAttribute(PRODUCIBLE_MEDIA_TYPES_ATTRIBUTE)`（"成功与失败的响应可以用不同内容类型"）。→ **契约的失败形态表成立**，相关用例按 200 + JSON 写。
4. **统计类工具自带 `--self-test`**：过滤器样本里**故意含一个 U+FFFD**，必须数得出来才通过 —— 防"统计坏了稳定打 0、被读成没乱码"。这类"判据工具本身坏了却不报错"的失效模式，是乱码类用例最大的假阴性来源。
5. **撞上 100 轮上限**（但报告已通过 SubagentHandback 交付）。与前端那次（35 轮上限、无报告）相比，这次没有损失 —— 因为它在撞限前完成了交付。
6. 顺带确认了两处环境事实并写进前置：`docker-compose/.env.local` **不存在**（容器内 `DEEPSEEK_API_KEY` 字节数 = 0 ⇒ 云端那半前置未满足，而"无密钥"正好是 2.3-4 要造的负路径）；**镜像里已含 `proxy_buffering off`**（`51: proxy_buffering off;`）。另标注了 `docker compose` 那句 `The "model" variable is not set` 是**阶段0 遗留噪音**（`docker-compose.yml:111` 未转义的 `${model}`），免得被当成阶段2 故障。

## 下次怎么改进

1. **★ 写测试案例前，先把每条判据"自己跑一遍" —— 而不只是把它写下来。**
   本次 415 缺陷就是这么撞出来的：判据本身（"看到 415 就知道是 Content-Type 没带"）是**文档写着的**，但没人真跑过，一跑就发现现实是 500。这与本项目既有的那条纪律同源（"判据自身的缺陷，静态复核与单测照不到，只有真跑一遍会撞上"），本次再次验证。
   判据：**用例里凡是"看到 X 就说明 Y"的推断，X 必须是自己亲眼见过的输出**，不能引自文档。
2. **派活时给的"造法/步骤"，派活人自己要先走一遍 —— 尤其是多步交互路径。**
   本次坑 2（401 造法）的根因是主会话凭对"受保护路由"的直觉写了造法，**没考虑路由守卫会先发一个 axios 请求**，于是造法根本不落到目标请求上。
   判据：**给"操作类"步骤时，问一句"这条路径上会不会先触发别的请求/别的守卫"**。
3. **统计/判据类工具一律自带 self-test，样本里故意植入要检出的那个坏值。**
   本次的 U+FFFD self-test 是正面样板。通用化：**凡是"数出来是 0 就算通过"的判据，都要能证明"数得出非 0"** —— 否则工具坏了和结果干净无法区分。
4. **"测不出来"要连替代验证方式一起交，不要只写"无法覆盖"。**
   本次 6 项全部给了替代路径（靠单测 / 取不到不算 FAIL / 走另一条端口）。**只写"测不了"等于把问题原样退给读者**；给了替代验证才是闭环。
5. **无害性要写成"我做过什么"而不是"我没做什么"。**
   本次 §0.1 逐条列出探针的具体形态（哪个接口、什么方法、预期什么），并明确"未登录/未写 Redis/未重建容器"。**正面清单可被核对，反面声明不可被证伪** —— 对"资质性红线"这类要求，前者才是有意义的证据。
