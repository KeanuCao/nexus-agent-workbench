## 遇到的坑

- **设计文档 §5.2 的版本号已过时**：文档写 Vite 5.x / Pinia 2.x / vue-router 4，而 npm 今日最新稳定版是 **vite 8.3.0 / pinia 4.0.3 / vue-router 5.3.1 / typescript 7.0.2**。agent 选择**按已批准的 §5.2 落地**（不擅自升大版本），并给出三条硬理由：① builder 是 Node 20，vite 8 / plugin-vue 6 的 engines 要求 `^20.19.0 || >=22.12.0`；② vue-router 5.3.1 的 peerDependencies 要求 `vite ^7.3.0||^8.0.0`、`pinia ^3.0.4||^4.0.2` → 取它就得整套连锁升级；③ §5.2 是已确认选型。**结论合理，但 §5.2 本身需要修订**。
- **契约缺口（最有价值的一条）**：§5.3 只说"依赖探活失败返回 HTTP 503"，**未定义此时 `code` 的取值**。前端按"非 2xx 走 axios 错误分支"实现 → **`data` 不解包 → 降级时拿不到 `checks` 明细**，即"后端真实探活、不造假"最该被展示的时刻反而看不见。这是**跨端契约的真实空洞**，需后端补定义。
- **`status`/`checks.*` 取值域未定义**：示例只有 `"UP"`。若后端复用 Spring `HealthStatus`，还会出现 `OUT_OF_SERVICE`/`UNKNOWN`。前端用 `'UP'|'DOWN'` 联合类型 + 未知值降级为 `info` 样式（不崩），但类型需在后端落地后核对。
- **Node 版本漂移**：Windows 本地 **v24** vs builder 容器 **Node 20**，与 §5.2"两者同大版本"的意图相悖。已建议记入 `wsl.abc.md`。
- **自己无法验证自己的产物**：红线禁止 `npm run build`/preview，所以 `npm run type-check`（唯一能验证 TS 全量的手段）**没跑过**。为此主动做了一个取舍：`scripts.build` 用 `vite build`（**不含** `vue-tsc`），因为 `vue-tsc -b && vite build` 一旦有类型错误会让**容器构建失败**，而它无法事先验证；类型检查拆成独立的 `npm run type-check`。取舍透明、理由正当，但是**未验证状态的直接后果**。

## 下次怎么改进

- **设计文档写版本选型时必须标注"核实日期"**，并在落地前重新核对 npm/registry 实际版本 —— 本次 §5.2 与实际差了 3~4 个大版本，说明"待验证"的标注**没有被真正兑现**。
- **契约文档要覆盖错误分支**：只定义 200 的响应体是不够的，`HTTP 503/4xx` 时的 `code`/`msg`/`data` 必须一并定死。这次 503 的 `code` 未定义，直接导致前端在降级场景丢失关键信息。**写契约时对每个非 2xx 状态码都要问一句"body 长什么样"**。
- **派活时就把"跨平台 lock 可移植性"列为交付项**：本次 agent 主动做了（含 Linux 二进制、`npm ci --dry-run`），应固化为标准动作 —— Windows 生成、Linux 容器消费的 lock 文件，这是最容易在 CI/容器里翻车的点之一。
- **"禁止打包"类红线要有配套的验证替代方案**：本次因禁 build 而没法跑 `npm run type-check`，导致交付物处于未验证状态。后续派活时应明确"你能跑的最小验证是什么"（如 `tsc --noEmit`、`npm ci --dry-run`），别让红线变成交付质量的黑洞。
- **前瞻性约束要提前写入设计**：agent 主动指出"阶段1 引入 JWT 后 `/api/health` 必须免鉴权，否则 nginx 与 up.sh 探活会 401"。这类**跨阶段耦合**要么写进阶段1 设计，要么在阶段1 开工时必然踩坑。
