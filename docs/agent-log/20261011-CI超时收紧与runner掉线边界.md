## 遇到的坑

1. ★ **本次故障不在配置层，缩短超时治不了它**：2026-10-11 的 CI job "卡住"，
   根因是**测试发行版被 WSL 回收**（实测证据：每次命令进去 `uptime` 都是 `up 0 minutes`，
   journalctl 反复出现新的 boot 标记）⇒ runner 随之消失 ⇒ **没有人执行这个超时** ⇒
   job 在 GitHub 上挂到人工取消（14 分钟）为止。
   ⇒ 收到"超时太长了"这类诉求，先分清它优化的是**真卡死**的止损时间，与**掉线**是两条链路。
   这条边界已写进 workflow 注释与设计文档，防止后人误读成"超时收紧了所以不会再挂"。
   （防掉线的办法是让测试发行版**常驻**：开一个终端占住，已记入长期记忆。）
2. **5 分钟这个初值余量不足**（用户直觉给的值）：实测全程 ≈4.5 分钟（部署 192s + 冒烟 19.4s +
   其余 ≈30~60s）⇒ 5 分钟只剩几十秒，builder 重新打包或依赖重下就会**在部署中途被误杀**、
   环境停在半完成态。处置：用实测数据换成 **15 分钟（≈3 倍余量）**，用户接受。
3. **`180` 是高频噪声**：全仓 grep 出来一大片，真正同指的只有 2 处。这类"同指判定"必须逐条
   给理由 —— 否则要么漏改（别处还写旧值），要么误改（把分块步长、healthcheck 宽限一起改掉就是事故）。

## 下次怎么改进

1. **值类改动（超时 / 阈值 / 端口）派活时，把"全仓同指 grep + 逐条判定"写成必交交付物**
   —— 本次能放心说"没有别处还写着旧值"，靠的就是这份清单。
2. **环境层故障与配置层修正分开记**：出现"job 挂了"先问"是谁没执行这个超时"，再决定要不要动超时值；
   两件事同轮发生时，最便宜的防腐手段就是在注释/文档里把边界写死。
3. 主会话复核顺序（本次生效）：**先看 diff、再看 agent 报告** —— 报告里的"未发现冲突"
   要用 diff 与 grep 清单交叉验证，不能只看结论。
