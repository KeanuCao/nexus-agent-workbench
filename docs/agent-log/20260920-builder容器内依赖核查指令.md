## 遇到的坑

1. **`builder` 走 `profiles: ["build"]`，不能依赖"显式点名会激活 profile"这条路径。**
   项目里 `docker-compose.yml` 的注释与既有实测都写着"显式点名照样激活"，但那是**拼写敏感**的隐式行为。它选择**每条 compose 子命令都显式带 `--profile build`** —— 多打几个字，换掉一整类"命令看着对却没生效"的故障。
2. **★ 含 `$` 的命令**绝对不能**经 `wsl -d ... -- bash -c "..."` 包装执行。**
   该包装会吃掉内层 `$`（`docs/agent-log/20260903-step2-manifest.md` 已有留档）。因此这份清单**全部改为在 WSL 内直接执行**（第 0 段是 `wsl -d nexus-agent-workbench` 进发行版，之后各条都在 WSL 的 bash 里粘）。
   ⚠️ **由此产生一处需要注意的"两套写法并存"**：设计文档 `02-统一AI网关.md` §6.0 的 7 步用的是 `wsl -d ... -- bash -c "…"` 包装 —— 那套命令**恰好完全不含 `$`**，所以包装是安全的；而本份核查清单含 `"$(cat …)"` 这类展开，必须直连 WSL。**不要为了"统一风格"把任一边改成另一边**，判据是：**命令里有没有 `$`**。
3. **Q1-3 的第二条命令有前向引用**：它引用 `/tmp/verify/start-cp.txt`，而那个文件在 **Q4-1** 才生成。清单里已就地标注"若还没生成，先跳到 Q4-1 再回来"，但这类顺序耦合是编写多段式清单的常见隐患 —— 读者顺序执行会撞上。
4. **`spring-webmvc` 之外还有一个隐性的传递性缺口**：`jakarta.servlet-api` 在 `nexus-infrastructure` 里是 `provided`，而 **provided 不传递**。若 module-ai 的代码里出现 servlet 类型，必须在它自己再声明一条 `provided` —— 只补 `spring-webmvc` 是不够的。这条是它主动补的，设计文档里当时没有。
5. **刻意不用 `spring-boot-starter-web` 补依赖**：那会把内嵌 Tomcat 与整条 MVC 链带进一个非 start 模块，与 `nexus-infrastructure`/`nexus-module-system` 两个 pom 里已写明的"只取需要的类"取舍相冲突 —— 引用既有先例，而不是新立规矩。

## 下次怎么改进

1. **凡是要交给别人手工执行的命令清单，先用一个"含 `$` 与否"的判据决定执行形态。**
   含 `$`（变量展开、命令替换）→ 必须在目标 shell 内直接执行；不含 → 才可以用 `wsl -d ... -- bash -c "…"` 这类包装。**这条要写进清单抬头**，而不是留给执行者自己判断 —— 两套写法并存时，人会本能地想"统一一下"，而统一的代价是其中一套静默失效。
2. **多段式清单要显式做一次"前向引用检查"**：把每段生成的文件名与每段引用的文件名各列一张表，比对是否有"先引用后生成"。
   本次 Q1-3 引用 Q4-1 的产物就是漏了这一步。判据：**清单里出现的每个 `/tmp/...` 路径，都要能指出它由哪一段生成、是否在该段之前。**
3. **"核实某依赖在不在"要给三层证据，不要只给一层。**
   本次每问都给了：① 依赖树（声明层）② 本地仓库落地（下载层）③ **编译期探针**（真实可见性）。三层互证才能排除"声明了但没下下来""下下来了但不在类路径上"这类中间态。探针写法本身很简单（`printf` 一个只 import 目标类的 `.java` + `javac -cp "$(cat cp.txt)"`），值得沉淀成通用手法。
4. **补依赖时要顺手检查 `provided` 的传递性缺口。**
   `provided`/`test` scope 都**不传递**，所以"我依赖的模块已经声明过 X"不代表我能用 X。本次第 4 条坑就是这么发现的。判据：**每补一条编译期依赖，就问一句"它 import 的类型里，有哪些是我自己没声明的"**。
