## 遇到的坑

1. **设计正文提到的配置键没有落进 §6.2 的清单（本阶段第二次）**。
   现象：`embed-batch-size` 在 §3.9 的探针说明里出现过，但 yml 清单里没有；`allowed-extensions` 同样（第一段已收口一次）。
   处理：子代理**不发明键**、按"发现对不上的键就上报"办；主会话裁定这三个值（embed-model / batch-size / expected-dimension）
   **保持常量**——没有消费者的配置键不加，而"支持哪几种模型/批量多大"本就是实现细节。
   教训：**正文提到某个键，就必须落进 §6.2 的清单**；否则实现者要么私自发明、要么停下来问。
2. **"扩展名 + 内容检测双重判断"对 TXT 不成立**：Tika 对合法 GBK 文件很可能判出 `application/octet-stream`，
   拿它做交叉校验会把**正路文件误杀成 10201**。裁定：内容检测只对 PDF 成立，TXT 的"是不是文本"由编码探测回答。
3. **设计里的"尾块合并"是不可达分支**：`步长 = size - overlap` 下，尾块长度恒 > overlap（子代理用 7920 组
   `size × overlap × 长度` 穷举，触发 0 次）。裁定：分支保留（防御性）+ 注释写明，但**不再当用例**。
   教训：设计里"为了防止某种形态"加的规则，实施时要**先证明它能被触发**，否则就是死代码 + 一条假用例。
4. **Tika 4.0.0 的 API 与 3.2.3 不同**：4.0.0 的 `Detector`/`Parser` 只接受 `TikaInputStream`（`detect` 还多一个
   `ParseContext` 参数）。这给父 POM"不取 4.0.0"的取舍补上了**实证依据**（原先只是版本保守）。
5. **`overlap ≥ size` 会让第一个上传请求死循环**（步长为 0 或负）：`TextChunker` 构造期 `validate` 抛
   `SystemException`（fail-fast，启动即响，而不是等用户上传时烧掉请求线程）。
6. **日志重复的风险**：生成器与服务层都可能打 `[kb] 生成完成`。裁定：**只打一条**（编排层打、适配器不打，
   与阶段2 两个 provider 的分工一致），并且**不为一条日志给 `generate(messages)` 加参数** ——
   设计里那行的 `sources=N` 与检索行的 `hits=N` 是同一个数，两行相邻即可。

## 下次怎么改进

1. **设计的 §6.2（yml 清单）要当作配置面的唯一真源**：正文任何地方提到配置键，先落清单再写正文；
   子代理侧的纪律（"发现对不上的键 → 上报，不发明"）本次奏效，保留。
2. **"没有 mvn" ≠ "不能自检"**：把真实 jar 缓存在 `.tmp/<agent>/jars/` + `javac -encoding UTF-8 -cp ...`，
   能把编译期风险降到接近零。**后续段默认做这件事**（成本：一次 jar 下载；收益：构建轮次从 N 次降到 0 次）。
3. **探针要覆盖"分支是否可达"**：分块那类不变量适合网格穷举（本次 7920 组），能直接判死代码；
   对"防某形态"的规则，先穷举再决定它是否值得留。
4. **失败形态要逐条喂进探针**（本次 5 种：非 2xx / 网络类 / 上游错误报文 / 条数不符 / 维度不符）：
   这几种在真机上很难造，用假 HTTP 服务一次跑完，比留给 TC-03 手工造便宜得多。
