## 遇到的坑

1. **★ 主会话派活时的文字自相矛盾，被纪律拦下。**
   任务里 pom 那条的**项目符号标题**写「`nexus-start/pom.xml` 加 `starter-validation`」，而**同一行的括号**写「已按用户确认改为 module-ai 一条解决」。括号里的理由（"module-ai 是 nexus-start 的依赖，运行期自然进 fat jar"）**只有在 nexus-start 不加时才有意义** → 两句不能同时成立。
   Agent 按更忠实的一条（括号 + 与既有"只声明自己直接 import 的依赖"取舍一致）执行，并**在回报里明确标注为偏离**，没有静默挑一条。
   → 这正是 CLAUDE.md 那条纪律存在的意义：**如果没有它，这处矛盾会沉进代码，等到"为什么 validation 在 module-ai 却不见生效"时才发现。**
2. **设计文档两处编号与实际条目数不符**：§3.1 标题写「两条补充约束」实际列了三条；§3.2 标题写「三条时序规则」实际列了四条（第四条实为解析前提，不是时序）。→ 契约文档按**实际条目数**落地（§3.2 拆成「三条时序规则」+「一条解析前提」），主会话已回头订正设计文档。
3. **`AiModelRegistry` 注入 `List<AiModelService>` 会让应用起不来。**
   容器里**零候选**时 Spring 抛 `NoSuchBeanDefinitionException`（"expected at least 1 bean"）→ 应用直接启动失败。而本段恰好就是"注册表已就位、provider 未到"的窗口。改用 `ObjectProvider` 后后端照常启动（只打一条 warn），代价是漏配实现从"启动失败"变成"运行期可见的 `10200`"。
4. **`@ConfigurationProperties` 的 getter 命名有静默陷阱。**
   Boot 把 JavaBean 属性 `deepSeek` 归一成 `deep-seek`，与 yml 的 `nexus.ai.deepseek.*` 对不上时**不报错、静默不绑定**。所以 getter 必须叫 `getDeepseek()`（小写 s）。已在代码里写明「别改成 `getDeepSeek`」，防止后人"顺手修"。
5. **`AsyncConfig` 会顺带压掉 Boot 的 `applicationTaskExecutor`**（`TaskExecutionAutoConfiguration` 的条件是 `@ConditionalOnMissingBean(Executor.class)`，本 Bean 就是 `Executor`）。已核实本项目无 `@Async`、无返回 `Callable` 的接口，`SseEmitter` 路径不消费 MVC 异步任务执行器 → 当前无影响；已写进类注释，将来新增 `@Async` 需显式指定执行器。
6. **宿主无 `mvn` 也无 `javac`**（构建在 builder 容器里，属 devops 链路）→ 本段**无法编译验证**，只做了静态自查（POM/YAML 可解析、`management` 块完好、括号配平、无 `*` 导入、无 `_` 标识符）。**首次编译由 devops 的 `build-backend` 完成。**

## 下次怎么改进

1. **派活前自己先做一次"标题 vs 正文"一致性检查。**
   本次坑 1 的矛盾出在**同一个句子里**（项目符号标题 + 同行括号），比跨段落的矛盾更难自查，因为两半挨着、看着都像"强调"。判据：**一条要求里有两种写法时，问一句"这两句能同时成立吗"** —— 不能就必须只留一句。
2. **分模块注入一律用 `ObjectProvider`，不用 `List`。**
   当模块可能"只有一半到位"（注册表先落地、实现后到）时，`List` 的零候选行为是**启动失败**，而 `ObjectProvider` 是**延迟可见的降级**。判据：**注入的是"一组可扩展实现"而非"必然存在的协作者"时，选 ObjectProvider。**
3. **写完 `@ConfigurationProperties` 立刻把 getter 名与 yml 键名对照核一遍。**
   这类不匹配**不报错**，只表现为"配了却不生效"—— 与 nginx 缓冲、`switch` 漏 `break` 同属"静默失效"家族。判据：属性名里含连续大写字母（`deepSeek`、`mySQL`）时，一律显式核对归一化结果。
4. **定义端口接口时，失败语义必须和签名一起定死。**
   设计只写了"上游不可达 → error 帧"，却没规定**怎么从 provider 传到编排层**。agent 补的那条（统一抛 `BusinessException(20100)`）是本段最有价值的产出之一 —— 不补，两个实现会各抛一种异常。
   **配套：取消路径的异常必须显式豁免**（"取消后的 IOException 不算故障"），否则取消功能一上线就伴随假告警。
5. **拆段执行时，第一段的交付说明要显式列"留给下一段的缺口"。**
   本段交出了 3 个（503 出口 / 软上限定时器 / D10 透传），且每条都带"为什么本段做不了 + 建议落点"。这比"我做完了哪些"更有用 —— **下一段需要的是边界，不是清单。**
