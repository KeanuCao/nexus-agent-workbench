## 遇到的坑

- **主会话把一个未经核实的判断当成事实写进了派单 brief，被 agent 纠正**：我在 brief 里断言「0.3.4 `wsl.abc.md` + README **仍未开工**」。实际 `wsl.abc.md` **早在 2026-09-03 就已交付**（9012 字节、四段式齐备、6 条实测记录，与 0.1 同批）。task-decomposer **没有照抄，去核实了文件**，然后按事实写成"拆两半看"（`wsl.abc.md` ✅ / README 章节未做）。
  - **这是本次最有价值的教训**：错误信息的传播路径是「主会话想当然 → 写进 agent brief → 若 agent 不核实就会固化进文档」。这与草稿那 8 处错误**是同一类问题** —— 未核实的断言被当成前提使用。
- **agent 的持久记忆会过期，且不会被自动纠正**：task-decomposer 发现 `devops-engineer` 的记忆文件 `project-health-probe-findings.md` 仍写着「两条都还没修（2026-09-12 复核仍然如此）」，而 compose 里两条**都已修**。它按红线**没动该文件**（agent 记忆归各自维护），只做提示。
  - 讽刺之处在于：该记忆的标题正是"**对正在运行的环境做只读实测**得到的偏差" —— 实测得到的结论，在事实变化后**反而成了最像证据的过期信息**。
- **"已实现"与"已验收"极易被混为一谈**：四个脚本都跑得通、语法都过，很容易顺手勾上。本次靠显式的三态表把它们分开，且每一条"待验收"都写了**具体缺什么**，而不是笼统的"待验证"。

## 下次怎么改进

- **写入 agent brief 的每一条"事实"都必须先核实，或者显式标注为"未核实"**。本次我以肯定语气给出了一个错误前提；若 agent 顺从地照做，错误会被固化进正式文档。**派单方是错误信息的最大来源之一** —— 应与 agent 的输出同等接受审查。
- **状态记录一律用三态或更多态**（已实现 / 已验证 / 待验收），**不要用二态**（未开工 / 已完成）。二态在面对"代码写完但没跑过"这种最常见的中间态时，只能被迫说谎。
- **"待验收"必须写清具体缺哪一项**，不要写"待验证"了事。本次每条都点名了缺失的验证动作（负路径、端到端、WARN 归零），这才可执行。
- **agent 持久记忆需要定期对账**：记忆是对某个时点的快照，代码变了它不会自动更新。建议在阶段收尾时把"记忆里的结论 vs 当前代码现实"对一遍，尤其是那些**记录了"尚未修复"的记忆** —— 它们最容易变成误导。
- **"阶段外沉淀"要记但要隔离**：有价值的工程沉淀（如排查方法论）应记录，但**不应计入当前任务的验收面**。用独立的段落/标记区分，避免验收清单被稀释。
