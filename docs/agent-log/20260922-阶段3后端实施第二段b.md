# 阶段3 后端实施第二段 b（持久化 / 编排 / 接口）

- **Agent**：backend-engineer ｜ **耗时**：约 18 分钟 + 续跑约 2 分钟（两处收口） ｜ **task-id**：无（本段由主会话手工留档，未经 Stop hook 归档）
- **续跑原因**：首轮交付后主会话裁定要补两处收口（503 按码分流、文件名长度预检），故同一 agent 被 Resume 了一次；本留档覆盖两轮。

## 做了什么

1. **15 个类**（`com.nexus.module.ai.rag` 的 entity / mapper / dto / service / controller 五个新包）：
   `KbDocument`（MP 实体）、`KbDocumentMapper`（纯 BaseMapper）、`KbChunkMapper`（**不继承 BaseMapper**，
   两条自定义语句）、`VectorTypeHandler`、两个 Service 端口 + 实现、两个 Controller、五个线类型。
2. **两处收口**（续跑）：
   - `GlobalExceptionHandler.handleBusinessException` 加**按码分流**：`code=20100` ⇒ **HTTP 503**，其余仍 200
     （契约 §7.7 承诺 503、而实现给的是 200 ⇒ **改代码、不改契约**）；
   - `KbDocumentServiceImpl` 的预检段加**文件名长度校验**（>255 ⇒ `40001` + warn），
     把原先会落到 DB `VARCHAR(255)` 的失败从 **500「系统繁忙」**改成客户端可读的错误。
3. **自检（宿主无 mvn）**：编译自检 40 个源文件 **exit 0**；行为探针实测
   `20100→503 / 10202→200 / 40001→200 / 10204→200`、文件名 300 字符→40001 且正常名不误拒
   （用抛标记异常的 `DocumentParser` 证明预检未被误触）。
4. **装配实测**：真实 `TenantLineHandlerImpl` 下 INSERT 被注入 `tenant_id`、`IdType.AUTO` 回填 documentId=1、
   `ChunkHit` 的 `@ConstructorArgs` 映射正确、切租户后 `selectList=0` 且 `deleteById=0`（正是 10202 那一格）。

## 遇到的坑

1. ★ **jsqlparser 解析不了 pgvector 的 `<=>`**（本阶段最贵的一个坑，见设计 §9 风险 4）。
   现象：检索语句让**每条问答请求都抛 `MybatisPlusException`** —— 不是"租户条件没注入"那种温和失败。
   原因：jsqlparser 5.0 把 `<=>` 切成 `<=`（`OP_MINORTHANEQUALS`）+ 一个孤立的 `>`，而
   `TenantLineInnerInterceptor` 是"**先 `parserSingle` 解析、后注入**"。
   处理（四条边界全用离线探针测过）：① 元凶**只有 `<=>`**（`CAST(? AS vector)` 单独出现时正常 ⇒ 设计里的
   退路①"换 `?::vector`"**不对症、已作废**）；② 换 `<->`/`<#>` 能解析但索引是 `vector_cosine_ops`，不能换；
   ③ **项目自己的 `@IgnoreTenant` 救不了**（AOP 只让 `ignoreTable()` 返真，而解析在它之前 —— 实测"恒真照样 FAIL"）；
   ④ 只有 MP 的 `@InterceptorIgnore(tenantLine="true")` **短路在解析之前**（`InterceptorIgnoreHelper.willIgnoreTenantLine`）。
   ⇒ 落地：`search` 标 `@InterceptorIgnore` + **手写 `tenant_id`（两张表都判）**，无上下文 fail-closed。
   **连带代价**：D11 的"SQL 里不手写 tenant_id"在检索这一处退让 ⇒ 必须配一条**跨租户提问**用例兜住。
2. **契约与实现打架**：契约 §7.7 写"上游不可达 = HTTP 503 + 20100"，而既有的全局处理器把**所有**
   `BusinessException` 映射成 200 ⇒ 现状 `200 + 20100`。处理：**修代码**（按码分流），并逐点复核 16 个
   20100 抛出点、证明不影响阶段2（池满走自己的出口；provider 的 20100 在工作线程被转成 `error` 帧）。
   教训：**契约里的一句承诺，要去实现层找它的载体**；找不到载体就是打架，不是"实现细节"。
3. **设计正文提到的配置键又一次没落进 §6.2 的清单**（本阶段第二次，第一次是 `allowed-extensions`）。
   现象：`embed-batch-size` 在正文出现过、yml 里没有；子代理按"发现对不上的键就上报、不发明"办。
   处理：三个值（embed-model / batch-size / expected-dimension）裁定为**常量**。
4. **`durationMs` 的语义按契约而不是按设计的示例**：设计 §4.11 的示例 `durationMs=48` 读起来像"只算 SQL"，
   而契约 §7.6 明写"含问题的向量化" ⇒ 按契约执行。**读示例会得出与契约相反的结论**。
5. **零偏移的时间戳渲染成 `Z` 而不是 `+00:00`**（`@JsonFormat(pattern="...XXX")`）⇒ 契约里"容器内通常为 `+00:00`"
   的措辞会在容器内**误导判据**（好在 `check-health.sh` 本来就按"不断言时区"实现，脚本没错）。
6. **同一件事在日志里有两种形态**：`tenant_id` 在 INSERT 的改写里是**字面量**（`tenant_id = 1`）、
   在检索语句里是**绑定参数**（`?`，因为它绕开了拦截器）。拿一种去核对另一种会误判成"没注入"。
7. **文件名超 255** 原先落到 DB 报错 ⇒ 500「系统繁忙」（客户端输入问题被报成服务端故障）。

## 下次怎么改进

1. **延续"真实 jar + javac"自检**（2a 立的做法）：本段 40 个源文件 exit 0，把编译期风险降到接近零。
   代价只是一次 jar 下载，收益是构建轮次从 N 次降到 0 次 —— 后续段默认做。
2. **凡"框架要改写我们的 SQL"的功能，先把最刁钻的那条语句拿去离线探针试解析**（本次 `<=>` 一测就现形）。
   这类冲突不会在编译期暴露，也不会在有数据的真机上"温和"出现 —— 它是**整条链路全挂**。
3. **设计文档的"正文提到某个键/某个语义"与"§6.2 清单/契约字段表"要对齐**：本阶段两次复发，
   根因都是"正文写细了、清单没跟上"。规矩：正文提到键 → 先落清单；正文的示例与契约冲突 → 以契约为准并上报。
4. **给"退让了结构化保证"的地方配一条机器判据**：检索语句手写了 `tenant_id` ⇒ 跨租户用例升为强制项。
   退让本身可以接受，**没有判据兜住**才是隐患。
