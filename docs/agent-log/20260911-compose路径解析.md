# compose 构建路径解析错误（frontend/frontend）

- **Agent**：devops-engineer ｜ **耗时**：约 7 分钟 ｜ **task-id**：ad321e8d00e35b805

## 做了什么

- 复现并定位报错 `resolve : lstat /mnt/c/wp/nexus-agent-workbench/frontend/frontend: no such file or directory` 的根因。
- **实测出 compose 三个路径字段的解析基准互不相同**：

| 字段 | 相对谁解析 | 本项目配置的实际结果 |
| --- | --- | --- |
| `build.context` | compose 文件所在目录 | `../frontend` → `<repo>/frontend` ✅ |
| `build.additional_contexts` 的本地路径值 | **同上**（compose 目录） | `./frontend` → `<repo>/docker-compose/frontend` ✅ |
| **`build.dockerfile`** | **已解析的 context**（不是 compose 目录） | `./frontend/Dockerfile` → `<repo>/frontend/**frontend**/Dockerfile` ❌ |

- **判定责任行是 `dockerfile: ./frontend/Dockerfile`**，不是 `additional_contexts`（后者路径实际存在，被排除）。
- **确认 `nexus-backend` 同病**：`<repo>/backend/backend/Dockerfile` 同样不存在。并说明"只报了 frontend"是因为 bake 遇首个错误即中止，**不能据此推断 backend 正常**。
- **解释了 `docker compose config` 为何漏检**：它不解析 `build.dockerfile`（输出原样保留相对路径），也不做任何路径存在性检查 —— bug 恰在其盲区。
- 给出修复（方案 A：`dockerfile:` 改为 `../docker-compose/<svc>/Dockerfile`，不动文件结构）与兜底方案 B，并给出可复用的静态预检命令。
- 全程未执行任何 build/up/run/pull，只用 `config` / `build --print` 等静态命令；未修改任何项目文件。

## 遇到的坑

- **本环境无外网**：Windows 侧与 WSL 内访问 `docs.docker.com`、`raw.githubusercontent.com` 全部超时/连接重置（curl exit 28，无 proxy 变量），**取不到官方文档原文**。devops 如实声明了这一点，改用**本机最小复现实验**取证 —— 结论反而比文档更硬（对着实际版本 compose v5.1.4 / buildx v0.34.1 实测）。
- **三个同类字段、三种解析基准**：`context` / `additional_contexts` 相对 compose 目录，`dockerfile` 相对 context。三者写法看起来一模一样（都是 `./xxx` 形式），极易误以为基准相同。**这是本次 bug 的认知根源。**
- **一个漂亮的旁证**：`builder` 服务写 `context: ./builder` + `dockerfile: Dockerfile`，拼出 `<repo>/docker-compose/builder/Dockerfile`（存在）—— 这解释了为何 builder 能构建成功，同时反证了规则是"dockerfile 相对 context"。**已成功的服务可以当作对照组来反推规则。**
- **静态校验存在系统性盲区**：此前多轮"`docker compose config` 校验通过"给了虚假的安全感，而 bug 就在它不检查的环节里。校验通过 ≠ 配置正确。
- **"bake definitions reading from stdin 1.12kB" 被用作证据**：devops 用日志里的字节数（1125B ≈ 1.12kB）反证送入 bake 的正是"已把路径拼成绝对的"那份配置，而非 raw compose（676B）。**从日志的边角信息里取证**，思路值得学。
- **不能真跑 build 导致唯一残留假设**：buildx 能否读取"位于构建上下文之外"的 Dockerfile 未能实测（原设计已依赖该能力），已明确标注为未验证推断。

## 下次怎么改进

- **把 `docker compose build --print` 的路径存在性预检固化进 `check-env.sh`**（替换或并列入设计文档 §4.2 第 6 项的 `config --quiet`）。修前实测 2 个 MISS、修后全 OK，一条命令即可拦住本次这类错误。**这是本次最有价值的产出，必须落地，否则同类问题还会再犯。**
- **凡配置中出现"多个写法相似的路径字段"，必须逐个实测其解析基准**，不能假设一致。可用 `build --print` / `config` 的输出直接观察拼装结果。
- **已跑通的服务是宝贵的对照组**：遇到"某个服务行、某个不行"时，对比两者配置差异即可反推规则，比查文档快且准。
- **静态校验通过不等于配置正确**：应明确每种校验手段"检查了什么、不检查什么"，把盲区记进文档。设计文档 §4.2 的校验项清单需要补上这一步的说明。
- **离线取证的替代路径**：取不到官方文档时，**用最小复现实验 + 二进制/日志旁证**替代，并如实标注"未验证的推断"部分 —— 本次做法可作为规范。
