# 阶段3 上传 415 的根因与修复（FormData 被 JSON 化，文件字节从未发出）

- **Agent**：`backend-engineer`（复现定位 + 后端处置 + 行为探针）｜`frontend-engineer`（前端两处处置 + 实测取证）｜
  **主会话**：派出与裁定、设计稿口径订正、提交
- **触发**：用户手动走查（8088）上传，报「请求格式不支持，请使用 application/json」
- **结论**：**文件字节从未离开浏览器** —— `FormData` 被 axios 当成 JSON 序列化成了 **11 字节**的 `{"file":{}}`

## 现象

走 `8088` 上传验收夹具，前端 toast 显示「请求格式不支持，请使用 application/json」——
**这句提示本身是误导**：它来自后端的 `HttpMediaTypeNotSupportedException` 文案，读起来像"你该用 JSON"，
而正确动作恰恰相反（让请求头带上 boundary）。

## 日志/证据（根因链，三段，均为源码级实测）

1. **`transformRequest` 把 `FormData` 变成 JSON 字符串**（`axios/lib/defaults/index.js`）：
   `isFormData(data)` 为真时 `return hasJSONContentType ? JSON.stringify(formDataToJSON(data)) : data`。
   实例默认头是 `application/json`（`request.ts`）⇒ 走了 `JSON.stringify` 分支。
   **实测取证**（frontend-engineer 在适配器入口打点）：修前 **body = 字符串 `{"file":{}}`（11 字节）**、
   修后 **body = 真 `FormData`**。
2. **"是 `FormData` 就删掉该头"那段永不触发**（`axios/lib/helpers/resolveConfig.js`）：
   它判断的是 `data instanceof FormData`，而经过第 1 步后 `data` **已经是字符串**了 ⇒ 条件永假 ⇒
   请求头留在 `application/json`。
3. **后端在映射阶段就拒收**：`consumes = multipart/form-data` 是**映射条件**，请求头不对时
   **根本到不了 `MultipartException`**，抛的是 `HttpMediaTypeNotSupportedException` ⇒ 415。

**正确的两种写法**（都实测过）：① 上传处显式 `headers: { 'Content-Type': 'multipart/form-data' }` ——
这个**不带 boundary 的值**会被 xhr（`resolveConfig.js`）/ fetch（`adapters/fetch.js`）两个适配器删掉、
由浏览器补 `; boundary=…`；② 在请求拦截器里对 `instanceof FormData` 删掉该头。
**自拼 `; boundary=…` 同样是错的**：那个值只有浏览器知道；本版 axios 会连它一起摘掉，
所以"没炸"是 axios 兜底、不是写法正确。

## 官方文档出处

axios 1.20 的**发行包源码**（`node_modules/axios/lib/…`，逐行读过：`defaults/index.js`、
`helpers/resolveConfig.js`、`adapters/fetch.js`）—— 无外网环境下以源码为准，并以适配器打点实测互证。
后端侧以 Spring 的实际行为为准：`HttpMediaTypeNotSupportedException`（映射阶段）≠ `MultipartException`（解析阶段）。

## 结论与处置

| 侧 | 改动 | 证据 |
|----|------|------|
| 前端 | `api/kb.ts` 上传显式声明 `multipart/form-data`；`api/request.ts` 拦截器对 `FormData` 删头 | 修前/修后 body 打点对照；`type-check` exit 0 |
| 后端 | `GlobalExceptionHandler` 的 415 出口**按"该接口是否消费 multipart"分流**：multipart 接口给 **200 + 40001**（契约 §7.7 第 2 行），非 multipart 仍是 **415 + 40002** | `javac` exit 0；4 格行为探针全过（上传+json → 200/40001、上传+无 CT → 200/40001、`/api/chat/stream`+`text/plain` → 415/40002 回归、`@RequestBody` 阶段 → 415/40002） |
| 文档 | 设计稿 **4 处反向口径订正** + §12 变更记录；契约 §7.1 精度订正 | 见提交 `1daae2a` |

★ **设计稿是被订正的一方**：§5.1-2 初版写的是「**不要**把 `Content-Type` 写死成 `multipart/form-data`…
手工写死会**丢掉 boundary**」，且是全文**唯一**挂着「待实测确认」的一条 —— 照它实现就是把 415 原样写回来。
本次订正 4 处：§5.1-2 正文、§5 签名块注释、§3.9 探针①的注释、§5 文件表（`request.ts` 由「不改」改「改」）。

## 下次怎么改进

1. **凡"库会自动帮我做 X"的设计断言，必须实测再写进设计稿。** 本稿唯一一条留在"待实测确认"里的断言
   （axios 会自动删头），恰恰就是错的那条 —— 而且它有**反作用**：照它做会把 bug 写回来。
   ⇒ 设计稿里凡涉及第三方库行为的句子，要么标出处+实测，要么直接写成"实施时必须验证的一句话"。
2. **错误文案会被当成诊断依据**（"请使用 application/json" 让人往反方向查）。
   多义文案要补一句"正确动作是什么"——本次后端侧的分流出口即按此改。
3. **诊断与处置按角色派**（本次由主会话派出 `backend-engineer` 复现定位）：两个角色各自带**可复现的判据**
   回来，比主会话在对话里堆命令输出更快也更省对话。
