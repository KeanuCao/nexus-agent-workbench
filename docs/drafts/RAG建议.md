RAG的建议，我分四块说，尽量短。

**一、选型：手写，不引框架。** 和阶段2“不用Spring AI”保持一致。理由：阶段2你要展示的是“工厂+策略”本身；RAG你要展示的是“你懂分块、检索、拼prompt的每一步”。引LangChain4j或spring-ai-pgvector-store，等于把要展示的东西换成框架自带实现，面试时讲不出细节。手写成本不高：解析用tika，embedding调Ollama，pgvector存，检索一条SQL，拼prompt调DeepSeek——核心逻辑不到200行。

**二、范围：最小闭环，四条做到就停。**
1. 上传TXT或PDF。
2. 解析、分块（固定500字+50 overlap，先不做语义分块）。
3. 调Ollama `nomic-embed-text` 向量化，存pgvector。
4. 提问→embedding→TopK（5）→拼prompt→调DeepSeek→返回答案+引用片段。

多格式、多知识库、rerank、混合检索、增量更新——全部记backlog，不做。

**三、真正值钱的不是“跑通”，是“踩坑记录”。** 招聘信息写“熟悉RAG”，要的不是你调过API，是你踩过这些坑：
- PDF解析乱码、表格错位——怎么处理？
- 分块太大检索不准，太小丢上下文——你怎么调的？
- 检索不到时模型胡说——怎么加“检索不到就说不知道”？
- TopK设多少？为什么？
- 本地embedding和云端对比过吗？成本差多少？

**每踩一个坑，记一句“症状→定位→修法”。** 这些就是你面试的谈资，也是你写文章的素材。你思科Tier 3那套故障攻坚的方法论，用在RAG调优上，正好是降维打击。

**四、时间盒：3-4天，不超过。** Day 7-8后端跑通，Day 9前端最小页面（上传+提问+显示答案和引用），Day 10录视频写文章。第10天无论做到哪，停。

**最后一句：** RAG需求大是真的，但“会调API的RAG”内卷，“能解决落地痛点的RAG”缺人。你的优势不在“会搭”，在“能兜底、能调优、能讲清楚每一步为什么”。这正是你思科17年+创业5年攒下来的东西。

明天开始，先做上传+解析+分块，跑通一条TXT再说。
