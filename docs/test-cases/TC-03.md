## 8. 备注：本阶段的两处判据坑 + 阈值标定 + 日志口径

### 8.1 ★ 判据坑 ①：`retrieval.durationMs` **含"问题的向量化"**

契约 §7.6 明写：`retrieval.durationMs` 是"检索耗时（**含问题的向量化**）" —— 那一步是检索的固有成本，
拆开报反而少一半信息（设计 §4.9 第 2 条的同一条推理）。
⇒ **判据按这个口径写**：一次问答的 `durationMs` 应当覆盖"embedding 一次问题 + 那条 SQL"，
**不要**拿它当"SQL 有多快"的读数（那样会得出"检索很慢"的错误结论）。
⚠️ 那次 embedding 在 CPU 上是**百毫秒~秒级**（随负载漂移）—— 这句只是量级感觉，**不是判据**：
`TC-03-4.1` ④ 只要求 `durationMs ≥ 0`。
用日志对照时看 `[kb] 检索: … durationMs=…`（同一个数）与 `[kb] 生成完成: … durationMs=…`（生成侧，另一个数）。

### 8.2 ★ 判据坑 ②：`tenant_id` 在 mapper debug 日志里**有两种形态**

| 语句 | 租户条件怎么来的 | debug 日志里的形态 |
|---|---|---|
| INSERT `t_kb_document` / `t_kb_chunk`、列表、删除 | `TenantLineHandler` **改写 SQL**（结构化保证） | **字面量**：`INSERT INTO t_kb_chunk (…, tenant_id) VALUES (…, 1)`、`WHERE tenant_id = 1` |
| **检索**（`KbChunkMapper.search`） | **手写**在 SQL 里、由参数绑定（拦截器被 `@InterceptorIgnore` 短路：pgvector 的 `<=>` 让 jsqlparser 解析失败） | **绑定参数**：`WHERE c.tenant_id = ? AND d.tenant_id = ?` |

**拿一种形态去核对另一种会误判成"没注入"**（设计 §4.11 已记）。检索那一条的正确判据是
"**两张表都判**且是绑定参数"，而它能被信任的**唯一**理由是 `TC-03-4.3`（跨租户提问不得命中）。

### 8.3 阈值标定（设计 §3.9 探针 D 的五步）

步骤与记录栏见 `TC-03-4.5`。**结论落点**：本文件的 4.5 实测栏 + 设计 §11 第 8 条 +
`application.yml` 里 `score-threshold` 上方的注释（"初值 0.5 是起点不是结论"那句改成实际标定值）。
⚠️ 标定前后**必须重灌文档**吗？—— 不需要：阈值是**查询侧**的参数（应用层过滤），与已入库的向量无关；
只有改 **embedding 前缀** 或 **分块参数** 才必须重灌/重传（设计 §4.4 的两条配置注意事项）。

### 8.4 日志口径（读 `[kb]` 行时的三条纪律）

1. **不打印正文**：日志里没有分块内容、没有问题、没有答案 —— 所以"答案对不对"只能看响应体或页面；
2. **`chars=` 是字符数**（`String.length()`，UTF-16 单元），中文与"字数"1:1；
3. **一次上传 = 五条 info + N 条 debug**（向量化每批一条 debug；要看它得把
   `com.nexus.module.ai.rag.embedding` 临时调到 debug，yml 里默认只给 `rag.mapper` 开了 debug）。
