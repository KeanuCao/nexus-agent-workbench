### 0.1 命令执行上下文（2026-09-15 新增）

「步骤」栏的命令一律是 **WSL 内**的完整命令 —— **不含速记、不含省略**。两种跑法：

- **推荐**：从 Windows 先开一个 WSL 终端，此后每格命令**原样粘贴**即可：

  ```bash
  wsl -d nexus-agent-workbench
  ```

- **不想开交互终端**：给命令套一层前缀（前缀本身也是完整可粘贴的）：

  ```bash
  wsl -d nexus-agent-workbench -- bash -c "<把步骤栏的命令整段粘进来>"
  ```

每格命令**自带 `cd`**，只有两种上下文：compose 命令用 `/mnt/c/wp/nexus-agent-workbench/docker-compose`；脚本与 git 命令用 `/mnt/c/wp/nexus-agent-workbench`。（0.4-3 是唯一例外：那条在 **Windows PowerShell** 里跑，格内已标注。）

> ⚠️ **为什么写这么死**：TC-00-0.1-7 曾把步骤写成 `exec builder git-sync` 这类速记，执行者照着敲不出来、只能自行翻译成 `docker exec nexus-builder git-sync`，于是该用例的失败**无法归因**（分不清是产品缺陷、文档缺陷还是执行偏差）。**速记在「步骤」栏一律不允许。**

## 2. db-patch 工作流（0.2）

> **§2 前置说明 —— 沙箱纪律（2026-09-17 起，Test Harmlessness 改造）**
>
> **本节用例对真实 `nexus` 库、正式补丁目录 `db-patch/` 一律只读**；容器内 clone 也只在 0.2-0 ② 跑一次 `git-sync`（它按设计把 build 工作区强制对齐到远端 —— 恰恰是「跑完不留差异」的前提）；除此之外写操作全部落在两个自建的一次性作用域里，并在 0.2-7 内销毁：
> ① **沙箱库** `nexus_tc00_probe`（`CREATE DATABASE` 建 → `DROP DATABASE … WITH (FORCE)` 删）；
> ② **容器内临时目录** `/tmp/tc00-patches`（从夹具 `cp` 建 → `rm -rf` 删；探针补丁本体在 `qa/fixtures/db-patch/`，属测试资产目录，生产链路不会读）。
> 两个**已存在**的作用域开关把写操作收进去（不必改代码）：`NEXUS_PG_DB`（`PatchCli.java:207` 决定目标库）与 `NEXUS_PATCH_DIR`（`docker-compose/builder/db-patch-migrate:22` 决定补丁目录），注入写法 `docker compose exec -T -e KEY=VAL builder db-patch-migrate`（若本机 compose 的 `exec` 不接受 `-e`，等价写法是 `docker compose exec -T builder bash -c 'NEXUS_PG_DB=… db-patch-migrate'`；两者都只给这一条 exec 的进程注入变量，不改服务定义）。
>
> **为什么改**：旧口径靠「`DROP TABLE t_user, t_tenant, t_db_patch CASCADE` → 重跑补丁恢复」「篡改业务补丁 `202609131000_…` → `git checkout --` 还原」「往容器内 `/workspace/repo/db-patch/` 丢探针 SQL 与 README」造负路径 —— 三处注入点**都不是一次性对象**：中途失败或漏清理会留下半个环境，第三处更是延迟爆发的坑（下一次真实迁移判乱序 `exit 3`，`up.sh` 当场中止）。**判据一条没少**（退出码、`t_db_patch` 顺序与行数、种子数据、新旧 checksum），只是换了隔离维度。
>
> **退出码契约**（判据直接引用 `PatchCli` 类注释的决策表）：`0` 全部成功或幂等跳过｜`2` 已应用补丁 checksum 不一致｜`3` 时间戳早于已应用最大文件名（乱序）｜`1` 参数错｜`4` 补丁 SQL 失败｜`5` 连不上库｜`9` 未预期。
>
